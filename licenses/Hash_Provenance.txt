Integrity hash suite v3
=======================

Sources
-------
SHA-512: FIPS 180-4, sections 4.1.3, 4.2.3, 5 and 6.4.
https://csrc.nist.gov/pubs/fips/180-4/upd1/final
Game.Hashes.SHA512.pas implements the specified SHA-512 with native UInt64
arithmetic. The API limits total input to 2^64-1 bytes and writes the complete
128-bit bit-length field (including the upper three bits).

XXH3-128: seed-zero scalar algorithm, canonical big-endian high64 then low64.
https://github.com/Cyan4973/xxHash/blob/v0.8.2/xxhash.h
Port cross-checked against the equivalent hash-wasm 4.12.0 xxhash128.c source
and independently against upstream libxxhash 0.8.2 XXH3_128bits at runtime.
The BSD 2-Clause upstream notice is included in Game.Hashes.XXH3.pas.
Streaming holds only a 256-byte buffer plus eight accumulators. All boundary
paths use the actual XXH3-128 algorithm, not two XXH64 calls or truncation.
Small utility routines are deliberately not marked inline: FPC 3.2.2 can
miscompile nested inline expressions in this port. Delphi also follows the
explicit call boundaries; byte results are independent of compiler inlining.

BLAKE3: official specification and official reference vectors.
https://github.com/BLAKE3-team/BLAKE3-specs/blob/master/blake3.tex
https://github.com/BLAKE3-team/BLAKE3/blob/master/test_vectors/test_vectors.json
The complete public vector file is included as blake3-official-full-vectors.json.
It includes all three modes and 131-byte XOF results, not just digest prefixes.
Keyed mode requires exactly 32 bytes. Derive-key context consumes explicit UTF-8
bytes and uses DERIVE_KEY_CONTEXT then DERIVE_KEY_MATERIAL domain flags.
Every parent and leaf is initialized with the proper mode/key; ROOT is applied
only to root output. Output seeking uses the root output-block counter.
The incremental implementation maintains the canonical 1024-byte chunk tree.
It does not start worker threads; tree semantics are fully supported, while
parallel execution remains an optimization requiring separate benchmarks.

Memory lifetime
---------------
BLAKE3 key chaining values, chunk buffers, parent stack and temporary output
state are explicitly overwritten when no longer needed and in Destroy.
SHA-512 state, input buffers and schedules are also overwritten. Returned
TBytes or strings are caller-owned; callers must minimize copies and clear
sensitive byte buffers. Delphi managed strings cannot promise erasure of
all historical copies or compiler temporaries. No hash algorithm requires a
production key embedded in this unit. The test probe's key is a published
vector constant, never a production secret.

Compatibility
-------------
TXXHash64 and XXHash64Bytes remain explicitly named legacy helpers only.
The GAME-CONNECT-4/hashVersion=3 measurements must use TXXHash3_128/XXHash3_128Bytes;
renaming an XXH64 result as XXH3 is prohibited. SHA512Bytes returns 128 lowercase
hex characters, XXHash3_128Bytes 32; BLAKE3 default is 64 lowercase characters.
Hash/CRC results alone never grant a session, license, or server approval.

Verification
------------
Compile the actual Pascal CLI; never use a surrogate in its place:
  fpc -Mdelphi -O2 -Fu.. -FE<temp-dir> -FU<temp-dir> HashProbe.dpr
or:
  dcc64 -U.. -E<temp-dir> -N0<temp-dir> HashProbe.dpr
Then:
  python3 ../../GameWeb/scripts/verify-native-hashes.py --probe <compiled-path>
On platforms without libxxhash, pass --xxhash-library <path-to-upstream-library>.

The runner compares every case's SHA-512 against Python/OpenSSL and XXH3-128
against libxxhash. It checks official BLAKE3 unkeyed, keyed, derive-key, 131-byte
XOF and an output seek crossing a 64-byte boundary. Update boundaries include
1, 7, 31, 63/64/65, 127/128/129, 239/240/241, 255/256/257,
1023/1024/1025, 4093 and 65536 bytes. Extended vectors include a 64 MiB input.
HashProbe checks zero-byte updates, repeated finish and update after finish.
This verifies portable algorithms, not a complete Delphi/Windows product build.

Server distribution
-------------------
See services/vendor/hash-wasm-4.12.0/PROVENANCE.txt and
services/vendor/noble-hashes-1.8.0/PROVENANCE.txt for exact pinned dependencies,
licenses and asset verification. Historical xxh64 fixture columns are retained
only as explicitly named historical reference data; no v3 report accepts them.
