관리자 웹 인증 강화 (1~5 단계 중 1번)

기존 단일 관리자 로그인과 A/B/O 실행 규약은 유지합니다. 이 설정들은 관리자
웹에만 적용되며 사용자 EXE의 서버 Challenge 또는 라이선스 규약을 변경하지 않습니다.

1. 신뢰 프록시와 HTTPS
- WEB_ADMIN_TRUSTED_PROXIES: 기본 빈 값. 쉼표로 구분한 실제 프록시 IP/CIDR만 허용.
  IPv4, IPv6, IPv4-mapped IPv6 지원. 호스트명, 포트, zone ID, 잘못된 CIDR은
  시작 시 설정 오류로 거절합니다. 설정 변경 후 서버를 재시작합니다.
- 직접 연결 peer가 위 목록에 있을 때만 X-Forwarded-For / X-Forwarded-Proto를
  해석합니다. XFF는 오른쪽부터 검사하고 처음 만나는 비신뢰 주소에서 멈춥니다.
  비정상·과다 hop은 직접 peer로 되돌립니다. 임의 헤더만으로 IP/HTTPS를 변경할 수 없습니다.
- 프록시는 X-Forwarded-Proto를 실제 외부 프로토콜로 덮어쓰고 XFF를 올바르게
  추가하거나 재작성해야 합니다. 전체 인터넷 또는 일반 사용자 네트워크를 신뢰하지 마세요.
- WEB_ADMIN_REQUIRE_HTTPS=1: 인증과 인증 세션 사용에 HTTPS를 요구합니다.
  기본 0은 기존 localhost HTTP 사용을 유지합니다. 실제 TLS 소켓 또는 신뢰하는
  프록시의 단일 https 헤더만 인정합니다. 웹 서버의 내부 HTTP 수신은 기존대로입니다.
- WEB_ADMIN_SECURE_COOKIE=1: 응답 cookie의 Secure 속성을 강제합니다.
  REQUIRE_HTTPS=1일 때도 Secure가 강제됩니다. 직접 HTTPS/신뢰 프록시 HTTPS도 Secure.
  Secure cookie만 켜는 것은 서버의 평문 HTTP 접속 자체를 차단하는 설정이 아닙니다.
- 공개 운영 권장 예시 (반드시 실제 프록시 주소로 교체):
    WEB_ADMIN_TRUSTED_PROXIES=127.0.0.1/32,::1/128
    WEB_ADMIN_REQUIRE_HTTPS=1
    WEB_ADMIN_SECURE_COOKIE=1
  위 예시는 같은 장비의 프록시용입니다. 프록시가 없다면 그 주소를 넣지 마세요.
  WEBAUTHN_RP_ID / WEBAUTHN_ORIGIN도 실제 관리자 웹의 도메인/HTTPS origin으로
  기존 배포 설정에 명시하세요. TLS 인증서나 프록시를 자동 설치하지 않습니다.

2. 수명·폐기
- WEB_ADMIN_SESSION_MS: 기존 idle 수명, 기본 1,800,000 ms (30분), 5분~24시간.
- WEB_ADMIN_ABSOLUTE_SESSION_MS: 기본 43,200,000 ms (12시간), 5분~7일.
  계속 요청해도 최초 로그인 후 절대 수명을 넘을 수 없습니다.
  벽시계와 단조시계를 함께 사용하며 과거로 돌아간 시계는 세션을 거절합니다.
  HTTP 응답 cookie도 남은 idle/절대 수명까지만 갱신합니다.
- WEB_ADMIN_MAX_SESSIONS: 기본 2048, 16~100000. 초과 시 새 로그인만 503으로 거절.
- 역할의 ADMIN_SECRET / OPERATOR_SECRET / VIEWER_SECRET 변경을 다음 인증/정리에서
  탐지하면 해당 기존 세션을 폐기합니다. 서버 재시작 시에도 모든 세션이 사라집니다.
- WEB_ADMIN_CREDENTIAL_REVISION: 임의 운영 세대 문자열. 변경하면 모든 역할의
  기존 세션이 폐기됩니다. 세션 ID/CSRF 재사용을 위한 복원 기능은 없습니다.
- 기존 세션 개별 해제·다른 세션 해제·전체 해제 기능은 그대로 유지됩니다.
- 패스키로 로그인/재인증한 세션은 그 패스키의 폐기 상태도 확인합니다.
  SSE 알림 전송도 이 검사를 수행하며 정리 주기에서 종료됩니다.

3. 로그인 제한
- WEB_ADMIN_LOGIN_WINDOW_MS: 기본 300000 (5분), 1초~1시간.
- WEB_ADMIN_LOGIN_IP_MAX: 기본 20 (같은 주소의 모든 인증 시도).
- WEB_ADMIN_LOGIN_ROLE_MAX: 기본 200 (같은 역할의 시도).
- WEB_ADMIN_LOGIN_GLOBAL_MAX: 기본 1000 (모든 인증 시도).
  비밀번호·패스키 시작/완료·재인증을 함께 계산합니다. 역할을 아직 알 수 없는
  패스키 완료 요청은 unknown 역할 bucket에 들어가며 IP/전역 제한도 적용됩니다.
  성공 여부를 검사하기 전에 차감하므로 유효한 비밀번호도 제한 중에는 429입니다.
  응답 Retry-After 이후 재시도하세요. 거절 요청은 제한 시간을 연장하지 않습니다.
  서버 메모리의 한정된 표를 사용하며 계정을 영구 잠그거나 DB 차단값을 저장하지 않습니다.
  이것은 단일 서버 제한이며 인터넷 전반의 DDoS 방어 또는 HA 공유 제한은 아닙니다.

4. 중요 작업 최근 재인증 (선택)
- DESKTOP_ADMIN_REAUTH_REQUIRED: 기본 0. 1로 켜야 중요 관리자 수정에 적용됩니다.
  이전 DESKTOP_SECURITY_STEP_UP_REQUIRED 및 이중관리자 정책을 다시 켜지 않습니다.
- DESKTOP_ADMIN_REAUTH_MS: 기본 300000 (5분), 1분~30분.
- 새 비밀번호/패스키 로그인 자체도 최근 인증으로 인정됩니다. 시간이 지난 뒤
  보안 정책·서명키·A/B/O 후보 등록/활성화·모듈 기준·CI 키/증빙·배포 규약 등 보호된
  수정과 관리자 패스키 등록/폐기 요청이 오면 서버는 적용 전에 428을 반환합니다.
- 화면은 관리자 비밀번호 또는 이미 등록한 패스키 중 하나를 선택하는 재인증 창을
  표시합니다. 성공한 경우 거절된 요청만 한 번 다시 보냅니다. 취소하면 적용하지 않습니다.
  패스키 없는 기존 관리자도 비밀번호로 완료할 수 있습니다. 비밀번호가 없는
  패스키 전용 역할은 등록한 패스키를 사용합니다. 패스키 강제/2인 승인은 추가하지 않습니다.
- 재인증 API는 로그인 세션과 CSRF를 필요로 하며, 패스키 challenge는 해당 세션에
  결속됩니다. 재인증은 기존 세션의 절대 수명을 늘리지 않습니다.

5. 검증
node scripts/test-web-auth-hardening.js
- 신뢰 경계, IPv4/IPv6/CIDR 경계, 고정 시간 제한, 세션 수명·폐기 검사
- 임시 DATA_DIR + 임시 HTTP listener로 로그인·CSRF·역할 거절·재인증·429 검사
- 실제 HTTP body를 나눠 전송하고 수신 중 세션 폐기/만료/비밀번호 교체 후 수정 거절 검사
- 폐기된 세션의 release 업로드는 발행하지 않고 임시 파일 정리, 재인증 challenge 발급도 거절
- 실제 EC 서명 fixture로 패스키 재인증 및 다른 세션의 challenge 전용 거절 검사
- UI api 함수의 재인증 후 1회 재시도와 취소를 VM에서 실행
node scripts/test-security-admin.js
- 기존 단일 관리자/CSRF/선택적인 별도 글로벌 승인 동작 회귀 검사

실제 브라우저/물리 패스키와 운영 프록시의 배포 설정은 별도 확인이 필요합니다.
모든 Windows EXE 빌드 여부와는 독립적인 서버/UI 변경입니다.
