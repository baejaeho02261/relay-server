GameConnect 데스크톱 요청·재시도·저장소 계약 (#2)

1. 공통 원칙

services/desktopRequestProtocol.js가 요청 purpose 목록, 내부 SHA-512 receipt
fingerprint, 제한된 응답 캐시, 관리자 requestVersion 규칙을 관리합니다.
실제 TLS desktopConnect.Dispatch에서 operation/action을 이 목록과 대조합니다.
이 검사는 라우팅 목적 검사입니다. 역할·서명·세션·라이선스 권한은 각 서비스의
Gate/Auth/Live/RequireArtifact에서 다시 검사합니다. 공통 목록 자체가 인증을
대신하지 않습니다. 기존 서명 canonical 바이트와 기존 프로토콜 버전은 유지합니다.

전송 requestId와 업무 requestId는 다릅니다. GAME-CONNECT-4 외부 암호 프레임의
requestId/nonce/key는 연결 재시도마다 새로 만들고, 업무 응답 소실 복구는 내부
requestId 또는 challengeId/reportId 및 이미 서명한 본문을 그대로 사용합니다.
동일 외부 프레임 재전송은 CONNECT_REPLAY로 거절합니다.
같은 업무 식별자에 다른 목적·본문·서명·세션 토큰을 붙이면 재사용 충돌로 거절합니다.
재시도는 원래 결과의 복구이며 새 승인, nonce 재사용 승인 또는 lease 연장이 아닙니다.

2. 엔드포인트/동작별 계약

관리자 HTTP는 매 요청 현재 관리자 세션, CSRF 및 해당 변경 권한을 검증합니다.
필요한 재인증/승인 티켓은 별도 관리 정책을 따릅니다. 네이티브 동작은 암호화된
TLS 요청의 operation/body.action으로 표기합니다.

관리자 license create/reissue/revoke에 requestVersion:2를 보내면 requestId가
필수입니다. 이 배포의 단건 관리 UI는 세 동작에 모두 version 2와 requestId를
보내며, 응답을 잃은 폐기 요청도 같은 세션에서 같은 ID/본문으로 확인합니다.
이미 REVOKED로 새로고침되어도 이전 결과 확인 버튼을 제공합니다. 로그아웃이나
관리 세션 교체 시 보류 요청은 지웁니다. 기존 클라이언트의 requestVersion 생략
(또는 1)은 유지합니다. 이 경우에도
requestId가 있으면 동일한 영속 receipt 규칙을 적용합니다. ID 없는 기존 발급은
호환 동작이며, 응답 소실 뒤 다시 발급하면 동일 업무임을 서버가 추정하지 않습니다.
내부 감사 operation ID는 이러한 레거시 변경에도 생성하지만, 이를 요청의
멱등성 보장으로 과장하지 않습니다. 관리자 재시도 키는 현재 actor/세션에 묶이므로
로그아웃 후 다른 관리자 세션으로 바꾸어 같은 요청을 복구하는 용도가 아닙니다.

재시도 가능한 기간은 실제 권한 만료를 넘지 않습니다. 영속 receipt가 남아 있어도
폐기된 라이선스, 닫힌 일반 세션, 변경된 빌드 정책을 복구하지 않습니다.
라이선스 challenge가 이미 만료/정리되었다면 같은 업무 ID·본문으로 새 challenge를
받아 서명해야 합니다. release의 종료 확인은 일반 실행 권한을 주지 않습니다.
새 overlayVerify는 기존 heartbeat 규약에 따라 갱신될 수 있으므로, 같은 결과
복사 캐시로 가장하지 않습니다. B→O transfer commit 및 결과 복구는 별도 고정
식별자에 묶입니다. legacy close/abort 호환 동작은 유지하고 V3 cleanup만 30초로
제한합니다.

Authority/Report receipt는 프로세스 메모리에만 있으며 최대 2,048개, 각 30초입니다.
가장 오래된 receipt가 밀리거나 서버가 재시작되면 새 challenge가 필요합니다.
Authority receipt는 원래 decision 수명도 넘지 않으며, 더 최신 결과·정책 revision·
운영 revision·현재 artifact 거부가 우선합니다. Report receipt는 policy와 DLL
baseline의 ID뿐 아니라 실제 기준값 전체에 묶여 같은 ID의 기준값 보완도 감지합니다.

이미 REJECTED/terminate:true를 만든 보고서만 예외적으로 보존된 capability 해시로
원래 거부 응답을 복구합니다. 정확한 이전 요청 해시, 역할, 세션, 기기/PC, 공개키가
일치해야 하며 결과는 여전히 종료입니다. 이 경로는 새 측정, 성공 응답, 세션 갱신,
license 승인에 사용되지 않습니다. 성공 receipt는 정상 Auth를 다시 통과해야 합니다.

3. 만료와 시계

license challenge/임시 verify receipt, Authority challenge/decision, Report challenge,
신규 응답 receipt는 desktopDeadline의 서버 wall clock + monotonic clock 중 먼저
끝나는 기한을 적용합니다. 파싱/RSA 검증 및 권한 gate 이후, 소비 직전에 재검사합니다.
클라이언트 시각은 기한을 늘리지 않습니다. 기존 canonical의 expiresAt은 그대로입니다.
monotonic tick은 파일에 저장하거나 재시작 시 임의 복원하지 않습니다.
기존 영속 launcher/flow/overlay/lease의 wall-clock 필드는 기존 호환 형식을 유지합니다.
이번 변경을 전체 영속 시각을 monotonic으로 마이그레이션한 것으로 해석하면 안 됩니다.

4. 라이선스 → flow → 감사 로그 연결

redeem/release는 GAME-LICENSE-OP-V1의 고정 operation ID와 원래 journal revision을
사용합니다. 하나의 라이선스 journal commit 안에 상태 변경, 업무 receipt, 민감정보를
제외한 audit intent를 함께 기록합니다. 관리자 create/reissue/revoke도 고정 감사
operation ID를 같은 commit에 기록합니다.

런타임 단계:
  1) fsync된 라이선스 journal에 변경과 감사 intent 확정
  2) bootstrap flow의 licenseId/lastLicenseOperationId/revision 반영
  3) 해당 operation의 감사 행 append + fsync
  4) 새 append-only ACK receipt를 라이선스 journal에 fsync

ACK는 기존 업무 receipt를 수정하지 않습니다. 감사 intent에 키·활성화 토큰·원본
서명 입력은 넣지 않습니다. auditEventId는 operation에서 결정되며, 동일 ID의
다른 감사 내용은 충돌로 거절합니다. 이벤트가 fsync된 뒤 ACK 전에 종료되어도
다음 프로세스는 검증된 감사 체인에서 기존 행을 찾아 중복 기록 없이 ACK합니다.
JSON/SQLite mirror가 뒤처져도 권한 원본은 기존 journal입니다.

server.js는 DATA_DIR OS lock을 먼저 얻고, 저장소와 감사 체인 head를 복원한 후
ReconcileOperations를 실행하고 listeners를 엽니다. 재조정은 이미 소비한 키를
AVAILABLE로 되돌리지 않고, 닫힌 flow를 열지 않으며, 원래 lease/session expiry와
lastVerifiedAt을 연장하지 않습니다. 감사 기록/ACK 실패는 STORAGE_SAVE_FAILED로
응답하고 intent는 남습니다. 같은 요청 재시도 또는 다음 startup에서 복구합니다.
startup 재조정 실패 시 listener를 열지 않습니다.

감사 append가 실패하면 RAM chain head와 이벤트 방송을 먼저 전진시키지 않습니다.
부분 append는 원래 길이로 rollback+fsync합니다. rollback까지 실패하면 그 프로세스의
감사 쓰기를 AUDIT_RESTART_REQUIRED로 차단합니다. startup은 검증된 prefix 뒤의
마지막 미완성 행만 잘라 복구합니다. newline으로 끝난 손상 행이나 중간 손상 행을
정상 기록으로 만들지 않습니다. POSIX에서는 durable append의 디렉터리도 fsync하여
날짜별 감사 파일 이름이 ACK보다 늦게 지속되는 문제를 줄였습니다. Windows에는
기존 journal과 동일하게 POSIX 디렉터리 fsync를 적용하지 않습니다. 시험은 프로세스
강제 종료와 I/O 장애를 검증하며, 모든 저장장치의 전원 차단 내구성을 보증하지 않습니다.

새 outbox는 이 버전에서 작성한 license 작업부터 적용됩니다. 기존 과거 receipt에
없던 감사 intent를 만들어 과거 손실 감사 행을 복원했다고 주장하지 않습니다.
운영자가 이미 ACK한 감사 파일을 삭제하거나 오래된 백업만 복원하는 행위까지
복구하는 원격/WORM 감사 저장소는 이번 단계의 구현 대상이 아닙니다.

5. 단일 작성자 운영

동일한 로컬 DATA_DIR는 .desktop-single-writer.sqlite의 SQLite BEGIN EXCLUSIVE로
프로세스 생존 기간 동안 하나의 서버/변경 도구만 소유합니다. 먼저 얻지 못하면
키 생성, migration, listeners 전에 중단합니다. 프로세스 종료 시 OS가 lock을
반납하며 PID 추정이나 stale lockfile 삭제로 우회하지 않습니다. TLS rotation 및
SQLite import CLI도 같은 lock을 사용합니다. 잠금을 유지한 상태에서 데이터와
감사 기록 종료 작업을 끝냅니다.

실행 중 coordination SQLite 본체·journal·sidecar를 삭제, rename, 복원하거나 다른
파일로 교체하지 마세요. local filesystem의 SQLite 잠금 보장이 전제입니다.
이것은 다중 노드 fencing/HA 구현이 아닙니다. 기존 HA refusal을 유지합니다.

  monotonic 만료, 같은 baseline ID의 값 변경, 실제 저장소 lease 불변.

  프레임을 사용한 동일 내부 report 복구, 외부 프레임 재전송 거부.
- test-desktop-audit-outbox.js: JSON/SQLite × 5개 license action × 4개 장애 지점,
