실제 수신 경계와 제품 GPU 오류 시험

이 문서는 실행 방법이며 시험 성적서가 아닙니다. Linux에서 실행한 fixture 검증은 Windows Schannel, Delphi 컴파일, 제품 세션 또는 GPU 실행을 증명하지 않습니다.

1. 실제 Schannel / 수신 UTF-8·JSON·PE 경계

  1. RAD Studio에서 cozy.TlsReceiveProbe.dproj를 열고 classic Win64 / Release / Build를 선택합니다. 시험 전용 TLS define, Schannel 대체 함수, CA 저장소 변경은 없습니다. 출력은 build/tests/manual-ide/cozy.TlsReceiveProbe.exe이며 DCU는 이 프로젝트 전용 디렉터리입니다.
  2. Windows x64에서 Node.js와 OpenSSL을 준비합니다. 아래 명령은 이미 빌드한 probe만 실행하며 컴파일하지 않습니다. 새 결과 파일 경로를 지정합니다.
cd Relay Server
node tools/native-receive-fault-tests.js --probe "..\Railway\build\tests\manual-ide\cozy.TlsReceiveProbe.exe" --output "native-receive-result.json" --openssl "openssl.exe"

전용 임시 디렉터리에서 1일 유효 localhost 인증서를 생성하고 무작위 루프백 포트를 엽니다. 실제 TRelaySocketClient와 TGameTlsStream이 인증서를 고정하고 Schannel로 수신합니다. 정확한 경계/초과 길이, 분할 UTF-8, 잘못된 UTF-8, 중복 JSON 키, 뒤따르는 객체, surrogate, 깊이, 정수 경계, LF 누락, 인증서 pin 불일치, fatal TLS alert, 잘린 handshake record, 실제 암호화된 application record의 인증 태그 변경을 검사합니다.

PE 두 사례는 TLS에서 받은 JSON의 base64 데이터를 CREATE_NEW·delete-on-close 파일에 쓰고 제품 TCodeIntegrity 파일 판독기로 검사합니다. 파일을 LoadLibrary하거나 실행하지 않습니다. 이는 A/B/O 다운로드·승인 전체 흐름이나 제품 lease 검증이 아닙니다. 결과의 productSessionLease는 NOT_RUN으로 남습니다.

각 결과에는 현재 실행 nonce, 실제 소켓 관측, 경계 반환값, 실패 후 transport 종료, 제한 시간과 probe SHA-512 전후 일치가 필요합니다. 출력 문자열의 PASS만으로 통과하지 않습니다. 플랫폼이 맞지 않으면 NOT_RUN입니다. 모든 실행에서 임시 인증서·probe 복사본·수신 파일을 정리합니다.

2. 제품 O의 GPU 실패 후 서버 세션 정리

일반 A/B/O 빌드에 fault define을 추가하지 마십시오. 별도 제품 fault 프로젝트와 GAME_PRODUCT_FAULT_TESTS;GAME_IMGUI_FAULT_TESTS 정의를 사용합니다. cozy.gpu-fault/cozy.game_imgui_fault_test.o 생성과 ELF 감사 방법은 기존 수동 시험 안내를 따릅니다. C++Builder classic Win64에서 cozy.gpu-fault/cozy.game_imgui_fault_test.cpp를 컴파일하며 옵션은 다음과 같습니다.

-std=c++11 -O2 -fno-exceptions -fno-rtti -fno-builtin -fno-use-cxa-atexit
시나리오실제 실행 위치관측 조건
gpu-create-e-outofmemory서버 Claim 이후 숨겨진 HWND에서 실제 D3D11 생성 시도E_OUTOFMEMORY 분류와 nil context. 첫 표시/READY를 요구하지 않음.
gpu-resize-device-removed첫 visible Present와 실제 READY callback 이후 UI 소유 스레드가 다음 ResizeBuffers를 요청실패 반환과 DXGI_ERROR_DEVICE_REMOVED
gpu-present-device-reset첫 visible Present와 실제 READY callback 이후 다음 실제 Present실패 반환과 DXGI_ERROR_DEVICE_RESET

오류 반환은 별도 C++ 시험 bridge에서만 주입합니다. armed 사건과 실제 반환을 확인한 fault-observed 사건은 구별합니다. renderer의 원래 예외·종료 흐름이 worker 취소, join, Close를 수행하고 제품 fault runner가 실제 fixture 서버의 authority 정리와 소유 프로세스 종료를 검증합니다. 일반 배포 artifact로 이 프로젝트를 게시하거나 승인하지 마십시오.

별도 제품 시나리오 tls-session-record-authentication-failure는 실제 A→B→O 이전이 확인된 후 시험 소유 루프백 TCP proxy를 한 번 활성화합니다. fixture 서버는 TLS 1.2로 제한하며 proxy는 이후 서버 application record 한 개의 마지막 암호화 바이트만 변경합니다. 정상 제품 Schannel이 거부하고 원래 lease/종료 경로를 따르는지 제품 runner가 검사합니다. plaintext 복호화·위조 응답·운영 서버 신뢰 정책 변경은 없습니다. 루프백 proxy 자체 시험 통과는 Windows 제품 실행 통과를 의미하지 않습니다.

물리 GPU 제거, 드라이버 TDR·복구, 모든 장치의 resource leak 검증은 NOT_RUN입니다. 이 실행은 실제 장치를 사용한 오류 반환 주입과 해당 제품 종료 경로의 범위만 평가합니다.

3. 이 환경에서 실행 가능한 fixture 자체 검증

cd Relay Server
node scripts/test-native-receive-fixture.js
node scripts/test-product-fault-tls-proxy.js

Node의 루프백 TLS로 바이트 전달 및 실제 암호문 변경을 확인하고 잘못된 nonce·누락 관측·비정상 경계 결과가 evaluator에서 거부되는지 검사합니다. 이 명령의 PASS는 fixture 자체 검증뿐입니다.
