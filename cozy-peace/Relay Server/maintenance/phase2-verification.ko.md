# 키 없는 서버 정책 연결 v2: 구현과 검증 범위

> 이전 단계의 기록입니다. 사용자 정의 서버 호출과 포인터 검증의 후속 변경은 `phase3-verification.ko.md`를 확인하세요. Windows 시험과 최종 발급 A 서명 제한은 계속 적용됩니다.

이번 소스는 `COZY_SERVER_POLICY_V2`와 공개 설정 형식 `COZYACF3`를 추가합니다. 새 A/B/O의 슬롯에는 역할·공개 정책 ID·해시만 넣습니다. 복호화 키와 정책 IR은 클라이언트 슬롯에 넣지 않으며, 새 Native 소스에서 기존 로컬 VM 복호화·실행 경로를 제거했습니다. 기존에 내려받은 VM v1 실행 파일은 자동 변경되지 않습니다.

서버는 정책 IR과 변환 기록을 정확한 A/B/O 바이트에 연결하고, 인증·기기·세션·무결성 검증을 통과한 요청에 기존 권한 조건을 적용합니다. 현재 런타임은 정해진 권한 조건을 호출합니다. 추가 사용자 정책·업무 함수를 등록하는 것만으로 해당 기능이 서버에서 호출되지는 않으며 별도 연결 구현이 필요합니다. EXE 전체 코드·함수·문자열 암호화나 임의 Delphi 함수의 자동 이전 기능이 아닙니다.

## 발급과 승인

새 A는 공개 연결 정보와 발급 ID만 포함합니다. 서버가 앱 키와 지속 기기 키의 서명, 파일·코드 측정, 일회용 요청과 만료를 확인한 뒤 관리자 승인을 기다립니다. 관리자가 별도로 확인한 고객·기기 신원을 승인해야 하며 현재는 **발급 A마다** 승인합니다. 이 승인은 고객 로그인 또는 TPM 증명의 대체물이 아닙니다. CNG 기기 개인키는 Windows 키 저장소에서 관리하고 평문 키를 소스나 EXE에 넣지 않습니다.

관리자 메뉴는 **구현 · 검증 · 종료 · 운영 성능 → 최초 기기 연결 승인 → 새 A 최초 기기 연결 승인 열기**입니다. 관리자 인증, CSRF, 동작별 최근 재인증과 공개 기기 지문 확인을 유지합니다. 승인 요청과 서명 재시도는 짧은 수명·개수·작업량 제한을 적용합니다. 오래된 증명은 시계 역행으로 되살아나지 않습니다.

새 VM v1 패킹·발급·운영 게시는 내장 키 때문에 거절합니다. 이미 발급한 이전 형식의 실행 경로는 호환 목적으로 남습니다. **v2 운영 게시도 `COZY_SERVER_POLICY_FINAL_ISSUED_SIGNING_REQUIRED`로 차단합니다.** 고객별 설정을 붙인 최종 A 전체 바이트의 서명 경로가 아직 완성되지 않았기 때문입니다. 이 보호 조건을 해제하는 것은 이번 작업에 포함하지 않습니다.

## 종료와 무결성

새 Native 소스의 사용자 오류 출력과 진단 출력을 줄이고, 잘못된 실행 인자를 초기 단계에서 거절합니다. 정상 Overlay 화면과 필요한 입력 기능은 유지합니다. 관련 세션의 만료·폐기·무결성 실패는 해당 조합의 권한을 종료합니다. 정상 B→O 인계와 선택 O의 정상 종료를 구분합니다. 주기적 보고에 실제 발급 A와 등록 B/O의 SHA-512·CRC64를 추가합니다. 이전 클라이언트가 생략한 비교를 완료로 표시하지 않습니다.

일시정지된 프로세스는 자신의 정리 코드를 실행할 수 없습니다. 서버 권한 만료와 Windows의 실제 종료·정리는 따로 검증해야 합니다. 프로그램 소유 자원만 정리하며 임의 파일 삭제, 프로세스 숨김, 외부 프로세스 포인터·레지스터 검사를 추가하지 않았습니다. 기존 정규화된 코드·파일·자체 포인터 구조 검증을 유지합니다.

## 검증과 남은 작업

격리된 서버 회귀 시험은 실제 SQLite, RSA 검증 워커와 로컬 HTTP/TLS를 사용하여 인증·승인·일회 소비·재전송·만료·재시작 후 상태·관련 세션 폐기를 검사합니다. 정책 연결은 별도 CPU 워커에서 실행하고 성공 결과의 버퍼 소유권과 늦은 결과 정리를 검증합니다. Docker 빌드가 소스 일관성·서버 수명주기와 관련 보안 시험을 실행하며 실패 시 배포를 중단합니다.

Windows 준비 도구는 `windows-signing.ko.md`를 참조합니다. 실제 Windows·Delphi 컴파일·A/B/O 실행·CNG·한글 Overlay·잔여물·Authenticode 서명은 이 환경에서 **NOT_RUN**입니다. 준비 결과와 Linux 검사를 운영 승인이나 실제 Windows 성공으로 사용하지 않습니다.

다음 단계는 최종 발급 A의 인증 가능한 서명 형식을 완성하고, 별도 Windows 환경에서 정확한 최종 A/B/O를 빌드·실행·종료 검증한 뒤 서명 바이트·새 승인·명세·게시를 연결하는 것입니다. 운영 키와 인증서 개인키를 저장소에 넣지 않습니다. 모든 취약점 또는 모든 잔여물의 부재를 보증하지 않습니다.
