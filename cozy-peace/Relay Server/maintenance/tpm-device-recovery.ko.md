# TPM 기기 등록·갱신·교체 운영 안내

2026-11-01. 이 문서는 TPM 기기 식별 복구에 관한 안내입니다. A 발급 서명 키 교체는 별도 기능입니다.

## 준비

- 이번 소스를 반영한 A를 기존 방식으로 빌드·승인·등록·게시하고 새 A를 발급합니다. 이미 발급한 EXE는 서버 배포만으로 변경되지 않습니다.
- 대상 PC에는 지원되는 TPM 2.0과 Windows Platform Crypto Provider가 있어야 합니다. 서버는 제조사 EK 인증서 체인, 인증서 용도·폐기 목록·유효기간, 요청 nonce에 연결된 키 증명과 자격증명 활성화를 실제로 검사합니다. 공급자 이름이나 키 소유 서명만으로 TPM 증명을 인정하지 않습니다.
- **관리자 웹 → 라이선스 관리 → 서버 복구 · 장치 · 저장소 → 영속 장치키 · TPM 서버 정책**을 엽니다. 팝업 제목은 **구현 · 검증 · 종료 · 운영 성능**입니다.
- **TPM 신뢰 설정 JSON**에는 검토한 공개 인증서와 신뢰 목록만 넣습니다. `roots`와 `intermediates`는 공개 PEM 인증서 배열, `revokedCertificateSha256`은 폐기 인증서 SHA-256 배열, `validUntil`은 신뢰 목록 갱신 기한인 UTC 밀리초입니다. 개인키·세션 토큰을 넣지 않습니다. 저장소의 합성 시험 인증서를 운영 신뢰 목록에 넣지 않습니다.
- TPM 필수 운영을 준비했다면 **최소 요구 수준 → TPM 2.0 키 증명 필수 → 서버 장치 정책 저장**을 사용합니다. 정책 변경은 이전 증명에 영향을 줍니다. 신뢰 목록이 없거나 만료되면 등록·복구를 거절합니다.

## 이번 A의 승인

1. 고객이 새로 발급한 A를 실행합니다. 서버 정책상 새 TPM 증명이 필요하면 A가 자동으로 증명을 준비합니다. 별도 BAT를 실행하거나 개인키 파일을 업로드하지 않습니다.
2. **라이선스 관리 → 서버 복구 · 장치 · 저장소 → 매 실행 기기 연결 승인 · 서버 정책 연결 A → 이번 A 실행 승인 요청 열기**를 누릅니다. 회원 관리 화면의 **매 실행 기기 연결 승인**에서도 같은 창을 열 수 있습니다.
3. **승인 대기 새로고침** 후 요청을 선택합니다. 요청 ID, A 발급 ID·SHA-512, 공개 기기키 지문과 앱 키 지문을 대조합니다. TPM 후보에는 기존 등록·기존 키, 새 키, 기기 연결 ID, 정책 revision 및 등록 종류가 추가로 표시됩니다.
4. 고객과 기기를 외부의 신뢰할 수 있는 수단으로 확인합니다. TPM 증명만으로 이전과 같은 물리 PC이거나 같은 고객이라고 판단할 수 없습니다. 회원 연결도 이 확인을 대신하지 않습니다.
5. 일반 고객·기기 확인과 **기존 등록·기존 키 및 새 키 대조** 확인란을 모두 체크합니다. **선택한 이번 실행 승인**을 누르고 관리자 재인증을 완료합니다.

| 등록 종류 | 처리 |
| --- | --- |
| `ENROLL` | 해당 기기 연결에 이전 키가 없는 최초 TPM 등록 |
| `RENEW` | 동일한 활성 키의 증명 만료 또는 신뢰 체인 변경 후 새 증명으로 갱신 |
| `REPLACE` | 잃어버리거나 교체한 이전 키 대신 확인한 새 TPM 키를 등록 |

잃어버린 이전 개인키의 서명을 요구하지 않습니다. 새 키의 실제 TPM 증명과 관리자의 이번 요청 확인은 반드시 필요합니다. 폐기된 동일 키를 다시 활성화하지 않습니다.

## Windows 키 저장소가 열리지 않을 때

키가 없는 경우 A는 현재 서버 키 이름에 새 키를 생성한 뒤 위 절차를 진행합니다. 기존 Windows 키 컨테이너가 손상되어 A가 새 키를 만들지 못하면, 고객과 기존 등록을 먼저 확인한 뒤 **영속 장치키 · TPM 서버 정책 → 폐기·복구할 장치키**에서 정확한 기존 키를 선택합니다. 실제 사유를 고르고 복구 확인란을 체크한 다음 **기존 장치키 폐기 · 선택한 복구 적용**을 사용합니다.

이 작업은 이전 실행을 폐기하고 서버의 키 이름 세대를 바꿉니다. 이후 새 A를 실행하면 새 이름의 키를 사용합니다. 화면에 표시되는 기존 15분 재등록 허용은 TPM 증명이나 이번 A의 별도 관리자 승인을 대신하지 않습니다. 새 TPM 후보에는 아래의 짧은 요청·승인 기한이 별도로 적용됩니다. 메인보드 교체 등으로 기기 연결 자체가 바뀌었다면 이 키 복구만으로 이전 PC와 같다고 연결하지 않습니다. 기존 장치 교체 절차를 별도로 검토해야 합니다.

## 승인 범위와 실패 시 처리

- 증명 단계는 30초, 전체 요청은 최대 5분, 승인 후 A 사용은 최대 60초입니다. 원래 요청·발급 만료가 더 빠르면 그 기한을 따릅니다. 재시도는 기한을 늘리지 않습니다.
- 승인은 정확한 이번 A·기기 연결·기존 키·새 키와 등록 상태에만 적용됩니다. **승인 버튼만으로 키를 교체하지 않습니다.** A가 실행 시작 검사를 통과하고 1회 발급을 소비하는 같은 저장 트랜잭션에서 등록·갱신·교체를 확정합니다.
- 교체 시 이전 연결의 실행 권한을 종료하고 이전 키를 폐기 상태로 남깁니다. 서버 권한 종료가 PC 프로세스의 즉시 종료·파일 삭제를 관측했다는 뜻은 아닙니다.
- 기존 PC 차단, 사용된 라이선스, 폐기 기록과 1회용 A는 그대로 적용됩니다. 이 화면으로 차단을 풀거나 라이선스를 복원하지 않습니다.
- 서버 재시작·배포는 아직 소비하지 않은 요청과 승인을 폐기합니다. A가 사용되지 않은 것을 확인하고 다시 실행해 새 요청을 검토합니다.

| 코드 | 확인할 내용 |
| --- | --- |
| `DEVICE_TPM_TRUST_NOT_CONFIGURED` | 신뢰 목록·갱신 기한과 서버 정책을 확인합니다. 임의 시험 루트를 추가하지 않습니다. |
| `DEVICE_TPM_REQUIRED` 또는 `DEVICE_TPM_*` | 실제 TPM·인증서·키 증명·활성화 실패를 점검합니다. 소프트웨어 키로 자동 우회하지 않습니다. |
| `DEVICE_RECOVERY_APPROVAL_REQUIRED` | TPM 후보의 정확한 기존·새 키 정보를 새로 조회하고 추가 확인란을 확인합니다. |
| `DEVICE_RECOVERY_CONFLICT` | 다른 등록·교체 또는 신뢰 상태 변경으로 후보가 오래되었습니다. 현재 상태에서 새 요청을 준비합니다. |
| `KEYLESS_REQUEST_EXPIRED` | 요청·증명·승인 기한 또는 정책 세대가 바뀌었습니다. 이전 승인을 재사용하지 않습니다. |
| `DEVICE_KEY_REVOKED` | 폐기된 키입니다. 기존 키를 재활성화하지 말고 검토한 새 키로 복구합니다. |
| `DEVICE_BINDING_RETIRED`, `DESKTOP_MACHINE_BLOCKED` | 기존 기기·PC 제한입니다. TPM 복구가 해제하지 않습니다. |

## 저장 범위와 검증 상태

서버에는 공개키·등록 상태·가명화한 기기 연결 및 감사 정보가 남습니다. TPM 개인키는 클라이언트 소스나 서버로 전송하지 않고 Windows가 관리하는 내보내기 금지 키로 유지합니다. 이 의도적인 OS 키 저장은 매 실행 기기 식별에 필요하므로 로컬 자료가 완전히 0이라는 의미는 아닙니다. 활성화 비밀값과 증명 준비 자료는 제한된 메모리에서 처리하고 사용·취소·만료 후 정리합니다. 운영자가 별도 개인키나 활성화 비밀값 파일을 만들 필요는 없습니다.

합성 인증서를 이용한 실제 암호 검증, worker 경로, 최초 등록·갱신·교체, 경쟁 요청, PC·라이선스 차단 유지, 저장 실패 원복과 취소 시 비밀값 정리 시험을 통과했습니다. 실제 Windows 빌드·물리 TPM 실행·A→B→O 실행 시험은 **NOT_RUN**입니다. 합성 시험 통과를 실제 기기 검증 완료로 표시하지 않습니다.
