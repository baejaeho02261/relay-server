# 최종 발급 A의 서명 연결

서버는 승인된 A 템플릿과 정확한 발급 설정을 함께 서명합니다. A는 네트워크 주소·TLS 핀·발급 ID를 사용하기 **전에** 자신의 파일에서 서명을 검증합니다. 개인키는 서버의 `DESKTOP_ISSUED_A_SIGNING_PRIVATE_KEY_B64` 변수에만 설정하며, A에는 그 키에 대응하는 공개 검증 키만 빌드합니다. 이 공개키는 비밀정보가 아닙니다.

이 기능은 애플리케이션의 발급 설정 인증입니다. Windows Authenticode, 게시자 인증서 또는 실제 Windows 실행 시험을 대신하지 않습니다. A/B/O의 기존 배포 승인·명세·일회용 소비·PC 정책·서버 인증은 유지됩니다. CI 기능은 사용하지 않습니다.

## 적용 순서

전체 소스 공급본에는 기본 발급 공개키를 넣지 않습니다. `Cozy.IssuedA.Trust.inc`는 설정 필요 표식이며, 공개키를 적용하지 않은 상태의 빌드는 `COZY_ISSUED_A_PUBLIC_KEY_SETUP_REQUIRED`로 중단됩니다. `Cozy.IssuedA.Trust.bin`과 `Cozy.LauncherResources.res`는 공개키 적용·빌드 과정에서 생성하므로 공급본에 포함하지 않습니다. 서버에 기존 복구 키가 ACTIVE이면 새 키를 만들지 않고 `Cozy.Finish-IssuedA-Trust.bat`으로 그 공개키를 적용한 뒤 표시된 정확한 프로젝트를 빌드합니다.

`Cozy.Finish-IssuedA-Trust.bat`과 복구 BAT의 공개키 적용 단계는 현재 공개키로 `Cozy.LauncherResources.res`까지 미리 생성합니다. Node.js가 필요하며, 공개키 RCDATA 311·현재 manifest·버전 정보를 함께 검증합니다. `완료: A 공개 include·bin·Cozy.LauncherResources.res를 갱신했습니다.` 출력 뒤 A를 Win64 Release로 빌드합니다. 이전 키를 가진 정적 `.res`는 배포하지 않습니다.

1. 전용 RSA 2048, 공개 지수 65537 개인키를 서버 변수 `DESKTOP_ISSUED_A_SIGNING_PRIVATE_KEY_B64`에 설정합니다. 값은 PKCS8 PEM 전체 바이트의 표준 Base64입니다. 전송용 TLS/RSA 키 또는 EXE 배포 승인 키를 재사용하면 목적 충돌로 거절합니다.
2. 같은 키의 **공개키만** `Cozy.Source/Cozy.Configuration/Cozy.IssuedA.Trust.inc`에 반영한 최신 전체 소스로 A를 Win64 Release 빌드합니다. 전체 소스에 포함된 공개키와 실제 서버 변수의 키 ID가 일치해야 합니다. 서버 변수 설정이 승인되지 않았거나 누락된 상태를 설정 완료로 취급하지 않습니다.
3. A/B/O의 서버 정책 연결, 최종 파일 승인, 최종 배포 명세 등록을 기존 절차대로 수행합니다. 서버 보안 · 배포 운영에서 새 A/B/O 후보 조합을 검증합니다.
4. 조합 검증은 A의 실제 PE 읽기 전용 섹션에서 공개키를 읽고 서버의 전용 키와 비교한 뒤 서명·검증 시험을 수행합니다. 새 검증기가 없는 A는 `ISSUED_A_BUILD_UPGRADE_REQUIRED`, 개인키가 없으면 `ISSUED_A_SIGNING_KEY_NOT_CONFIGURED`, 서로 다르면 `ISSUED_A_SIGNING_KEY_MISMATCH`로 거절합니다.
5. 게시 후 기존 **일회용 A 발급** 버튼을 사용합니다. 서버는 개인화된 최종 파일을 서명하고 재검증한 뒤, 그 최종 해시와 서명 봉투를 발급 기록에 함께 저장합니다. 다운로드는 저장한 봉투를 그대로 사용하므로 다운로드마다 새 서명이나 새 설정이 만들어지지 않습니다.
6. 새 최종 발급 A로 실제 Windows 실행·종료·일회용 재실행 시험을 수행합니다. Linux 소스 검사와 Node 암호학 시험은 이 실제 실행 결과를 만들지 않습니다.

이 변경만으로 이미 빌드한 구형 A에 검증기가 추가되지는 않습니다. 구형 unsigned V3 발급 기록은 읽기·이력 보존을 위해 유지하지만 새 다운로드와 미사용 A의 새 실행에는 서명을 요구합니다. 기존에 소비된 세션은 기존 서버 권한·만료·폐기 규칙을 계속 적용합니다. 오래된 비 V3 레거시 템플릿의 기존 발급 형식은 별도 경로로 유지합니다. 새 공개키 앵커가 있는 A를 레거시 형식으로 발급하려 하면 거절합니다.

## 공개키 도구

`tools/security/peace.issued-a-signing-key.js`는 개인키를 출력하지 않습니다. 모든 파일 경로는 절대 경로이고, 출력 파일은 기존 파일을 덮어쓰지 않습니다.

- `--action generate --private-key-file <소스 밖 새 PEM 경로> --public-json-out <새 공개 JSON 경로> --include-out <새 include 경로>`: 전용 키와 공개 산출물을 생성합니다. 개인키 파일은 소스 패키지 밖에 두고 서버에만 비밀로 전달해야 합니다. Windows에서는 새 빈 임시 디렉터리의 ACL을 먼저 제한한 뒤 그 안에 개인키 파일을 만듭니다. 제한된 파일 ACL을 유지하는 create-only 하드 링크로 게시하며, 이를 지원하지 않는 파일시스템에서는 실패합니다. 실패하면 해당 작업이 만든 파일만 정리합니다.
- `--action export --private-key-file <외부 PEM 경로> --public-json-out <새 공개 JSON 경로> --include-out <새 include 경로>`: 기존 키의 공개 정보만 내보냅니다.
- `--action include --public-json-file <공개 JSON 경로> --include-out <새 include 경로>`: 공개 JSON만으로 Pascal include를 생성합니다. 생성한 내용을 확인한 뒤 기존 `Cozy.IssuedA.Trust.inc`를 교체하고 A를 다시 빌드합니다.

키 회전 시 새 공개키를 포함한 새 A 템플릿을 승인·게시해야 합니다. 이미 서명한 발급 파일은 저장된 봉투와 기존 템플릿 공개키로 검증되며 새 개인키로 다시 서명되지 않습니다. 이전 A의 실행을 폐기하려면 아래 세대 관리의 REVOKED 또는 기존 배포 조합·파일 폐기 정책을 사용합니다. 단순히 서버 개인키를 변경하는 것은 기존 공개 서명을 무효화하지 않습니다.

## 파일 규격

최종 파일은 `승인된 템플릿 || V3 공개 설정 || 184바이트 헤더 || RSA 서명 256바이트 || 13바이트 footer`입니다. 공개 설정의 상한은 8,192바이트이며, **최종 파일 전체**는 기존 무결성 검사와 동일하게 64MiB 이하여야 합니다. 게시 준비 검사는 설정·서명 공간 8,645바이트를 미리 예약합니다. Footer는 정확히 ASCII `COZYA4SIGNED!`입니다.

| 헤더 위치 | 길이 | 값 |
| --- | --- | --- |
| 0 | 16 | ASCII `COZY-ISSUED-A-V1` (NUL 없음) |
| 16 | 4 | 템플릿 길이, little endian |
| 20 | 4 | 공개 설정 길이, little endian |
| 24 | 32 | 공개 CNG RSA blob의 SHA-256 |
| 56 | 64 | 템플릿 전체 바이트 SHA-512 |
| 120 | 64 | 공개 설정 전체 바이트 SHA-512 |

서명은 헤더 전체의 SHA-256에 대한 RSA PKCS#1 v1.5입니다. 서명 자체를 포함한 파일 해시를 서명 입력으로 다시 넣지 않으므로 순환 해시가 없습니다. 최종 파일 SHA-512는 서명 완료 후 서버 발급 기록에 저장합니다.

공개키 앵커는 읽기 전용·비폐기 PE 섹션의 331바이트 상수입니다: ASCII `COZYAISSUERKEY1!` 16바이트, 키 ID 32바이트, Windows CNG `RSAPUBLICBLOB` 283바이트입니다. 앵커의 RSA 2048·지수 65537·키 ID를 검사하고 유효한 앵커가 정확히 하나여야 합니다. 설정이나 footer가 새 공개키를 선택하게 하지 않습니다. 외부 도구가 최종 파일을 검증할 때도 별도로 신뢰한 템플릿 해시와 키 ID를 지정해야 하며, 파일에 들어 있는 임의의 키만으로 신뢰를 선언하지 않습니다.

## 검증 범위

- Node 시험: 템플릿·설정·길이·키 ID·서명·footer 변경, 잘림·추가 바이트, 키 불일치, 중복·쓰기 가능·파일 끝에 덧붙인 앵커 거절.
- 실제 bootstrap 저장소 시험: 최종 서명 A 발급·반복 다운로드, 기존 두 키 소유 증명·관리자 승인·일회용 소비·서버 재시작 저장 검증.
- Native 시험 소스: `Cozy.Tests/Cozy.Security/Cozy.IssuedASignatureProbe.dpr`가 Windows CNG와 실제 파일 읽기로 동일 공개 벡터·변조·잘림·파일 위치 복원을 검사합니다. 실행하지 않은 환경은 NOT_RUN입니다.
- 공개키를 가진 로컬 실행 코드 전체가 공격자에 의해 교체되는 상황까지 자체 검사만으로 막는다는 보장은 하지 않습니다. 배포 승인, 서버 측 실행 권한, 파일 해시 결합과 Windows 플랫폼 보안은 계속 필요합니다.


## 발급 서명키 세대 관리

운영 목록에는 ACTIVE·RETIRING 키만 표시합니다. REVOKED 키의 행과 ID는 이 목록에서 제거하며, 서버의 철회 판정과 과거 발급 검증 기록은 계속 유지합니다.

배포만으로 운영 키가 교체되지 않습니다. 기존 단일 변수와 V1 검증기·파일 규격은 그대로 작동합니다. 관리자 웹의 **서버 보안 · 배포 운영 → 최종 A 발급 서명키 · 세대 관리 → 발급 서명키 상태 조회**에서 시작합니다. 이 조회는 등록·키 목적 예약·발급을 하지 않습니다. 개인키는 화면과 응답에 포함하지 않습니다.

| 상태 | 새 A 발급 | 기존 최종 A의 정확한 재다운로드·서버 사용 |
| --- | --- | --- |
| ACTIVE | 해당 키를 내장한 템플릿만 허용 | 기존 정책도 충족할 때 허용 |
| RETIRING | 거절 | 원래 발급 봉투를 그대로 사용; 이전 개인키 불필요 |
| REVOKED | 거절 | 서버 사용 거절; 관련 미사용 A와 실행 권한 철회 |

기존 발급을 보존하며 세대 관리 시작을 누르면 현재 기본 서명키를 ACTIVE로 등록하고 과거 발급 기록의 다른 키 ID를 RETIRING으로 보존합니다. 이 등록은 독립 bootstrap 권한 저장소의 인증된 journal에 저장됩니다. 일반 등록 초기화나 서버 변수 삭제로 세대 기록이 지워지지 않습니다. RETIRING → ACTIVE 및 REVOKED → 다른 상태는 허용하지 않습니다. 상태 변경에는 현재 revision, 최근 관리자 인증과 기존 작업 승인이 필요합니다.

### 새 키로 전환하는 순서

1. 먼저 **상태 조회 → 기존 발급을 보존하며 세대 관리 시작**을 실행합니다. 현재 키를 바로 철회하지 않습니다.
2. 기존 공개키 도구로 새 전용 키를 생성합니다. `Relay Server` 폴더에서 다음 형식으로 실행합니다. 모든 경로는 실제 절대 경로로 바꾸며, 개인키는 소스 폴더 밖에 둡니다. 이 도구는 Node만 사용하며 Delphi·CI 환경을 요구하지 않습니다.

   ```text
   node tools/security/peace.issued-a-signing-key.js --action generate --private-key-file <외부의_새_private.pem> --public-json-out <새_issued-a-public.json> --include-out <새_Cozy.IssuedA.Trust.inc>
   ```

   기존 외부 개인키에서 공개 JSON만 필요하면 `generate` 대신 `export`를 사용합니다. 공개 JSON은 `version`, `algorithm`, `keyId`, `publicBlob` 네 필드뿐입니다. 관리자 화면에는 이 공개 JSON만 붙여넣습니다.
3. Railway의 비밀 변수 **DESKTOP_ISSUED_A_SIGNING_KEYS_JSON**에 추가 키를 등록합니다. 값은 `{"<새 공개 keyId>":"<PKCS8 PEM 전체 바이트의 Base64>"}` 형태입니다. 기존 `DESKTOP_ISSUED_A_SIGNING_PRIVATE_KEY_B64` 값은 유지합니다. 이 두 변수에 같은 키를 중복 등록하면 거절합니다. 추가 변수는 최대 16개 키·192,000자이며 개인키 값은 서버 밖 공개 저장소·명세·웹 입력에 넣지 않습니다.
4. 관리자 웹에서 **상태 조회 → 새 발급 서명키 공개 JSON → 서버 설정과 대조해 새 키 등록**을 실행합니다. 서버는 키 ID와 실제 개인키 소유 증명·용도 분리를 검사합니다. 잘못된 키나 다른 용도의 키는 등록되지 않습니다. 전환 중에는 여러 ACTIVE를 허용하되 템플릿과 정확히 같은 키만 선택합니다.
5. 새 공개 include를 `Railway/Cozy.Source/Cozy.Configuration/Cozy.IssuedA.Trust.inc`에 반영하여 새 A 템플릿을 기존 방법으로 빌드·승인·게시합니다. 기존 빌드 단계의 `Cozy.Build/Cozy.Prepare-IssuedATrust.ps1`이 공개 리소스를 준비합니다. 서버 웹 체크만으로 기존 EXE의 공개키는 변경되지 않습니다. 새 키로 A를 배포하려면 새 A가 필요하며, 이 변경에서 실제 Windows 실행 결과를 대신 만들지 않습니다.
6. 새 A 발급과 실제 사용을 확인한 뒤 이전 키의 **기존 발급만 허용**을 눌러 RETIRING으로 전환합니다. 기존 템플릿을 다시 선택해 새 발급을 시도하면 거절합니다. 같은 발급 요청의 재시도는 원래 파일과 해시를 유지합니다. 이때 이전 개인키를 서버 변수에서 제거해도 기존 봉투 검증·허용된 재다운로드는 계속 가능합니다.
7. 이전 키의 모든 발급·실행을 중단하려는 경우에만 **이 키의 발급·실행 철회**를 사용합니다. 확인 후 REVOKED로 저장하며 복원할 수 없습니다. 새 서명키를 등록하고 새 템플릿을 사용해야 합니다.

REVOKED는 서버 권한과 다음 인증 요청을 차단합니다. 고객 PC가 오프라인인 동안 서버가 파일을 변경하거나 프로세스를 강제로 종료했다고 표시하지 않습니다. 기존 V1 자체 서명 검증은 바이트의 진위를 확인하며 서버의 최신 철회 상태를 오프라인에서 알 수 없습니다. B/O의 연결 권한은 부모 A의 세대를 다시 검사하며 종료 관측과 파일 정리는 기존 별도 기록을 유지합니다.

### 조합 검증에서 RETIRING·REVOKED가 표시될 때

조합 검증은 선택한 A 파일에 내장된 공개키를 사용합니다. 서버에 새 ACTIVE 키를 등록하거나 공개 include를 갱신해도 이미 빌드·등록한 A의 바이트는 바뀌지 않습니다. 실패한 조합 검증에도 **A 내장 공개 키 ID**를 표시하므로 발급 서명키 상태 조회의 대상 키와 먼저 대조합니다. 유효한 공개키를 읽지 못한 A에는 키 ID를 표시하지 않습니다.

1. 새 발급에 사용할 키가 ACTIVE인지 확인합니다. **기존 발급만 허용**은 ACTIVE → RETIRING의 일방향 전환이며, 기존 발급 파일의 사용을 보존하면서 신규 발급을 중단하는 작업입니다. 새 발급을 준비하는 키에는 적용하지 않습니다.
2. 서버 키가 이미 ACTIVE이고 복구 BAT의 공개키 적용 단계만 실패했다면 `tools/Cozy.Finish-IssuedA-Trust.bat`으로 그 단계를 다시 진행합니다. 새 키 준비가 필요한 경우 `tools/Cozy.Recover-IssuedA-Key.bat`의 순서대로 서버 설정·공개키 등록·공개 검증키 적용을 수행합니다. BAT의 Enter 확인은 서버 자동 검증이 아니므로 실제 웹 상태와 키 ID를 확인해야 합니다.
3. 같은 공개키를 반영한 A를 기존 RAD Studio Win64 Release 방식으로 다시 빌드합니다. `Cozy.Build-All-Win64.bat`은 필수가 아닙니다.
4. 새 A를 `tools/Cozy.Check-IssuedA-Trust.bat`에 끌어 놓고 **웹에서 확인한 ACTIVE 공개 키 ID**를 입력합니다. 검사 도구는 A를 실행하지 않고 읽기 전용 PE 영역의 공개키를 대조합니다. 일치는 공개키 바이트 확인 결과이며 서버의 현재 상태·운영 게시 승인·Windows 실행 성공을 뜻하지 않습니다.
5. 새 A에 기존 서버 정책 연결·패킹 절차를 적용하고 최종 결과의 공개키를 다시 대조합니다. 파일이 바뀌었으므로 최종 파일을 승인하고, 최종 A/B/O와 일치하는 새 명세·후보를 등록합니다. 새 A 후보를 선택해 조합을 다시 검증합니다.

일반 등록 초기화는 인증된 발급 서명키 세대 기록을 삭제하지 않습니다. REVOKED를 초기화로 복원하지 않으며, 새 ACTIVE 키와 그 공개키를 내장한 새 A를 사용합니다. 키 상태를 변경하면 이전 조합 검증 결과는 무효화되므로 현재 후보를 다시 검증합니다. 개인키는 이 정적 검사에 필요하지 않습니다.

시험 범위: 실제 Node RSA 서명, 두 세대의 정확한 템플릿 선택, RETIRING 중 동일 발급 재시도, 이전 개인키 삭제 후 바이트 보존, REVOKED 시 미사용 A·실행 중 흐름 종료, 프로세스 재시작 후 철회 유지, 공개 입력 및 관리자 권한 검사. 키 회전과 실제 Windows 실행은 운영자가 수행한 경우에만 완료로 간주합니다.
