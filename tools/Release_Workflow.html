Game 처음 준비하는 순서

이 전체본의 Tools는 실행 전 상태입니다. 실제 spec.json·배포 정책·입력 관측/승인 기록·CI 공개키 JSON·실행 로그·ci-runs·승인/증거 JSON·개인키를 포함하지 않습니다. *.example.json은 입력 양식을 보여주는 소스 예제이며 실행 완료 기록이 아닙니다.

ZIP의 GameConnect_GameWeb_Fresh_Start_20261013 폴더를 기존에 없던 새 위치에 풉니다. 이 폴더가 이미 있다면 다른 새 위치를 선택합니다. 이전 Tools 폴더, 생성된 JSON, 로그 또는 CI 결과를 복사하거나 합치지 않습니다. GameWeb와 GameConnect_Win64는 같은 상위 폴더에 둡니다.

소스 밖에 보관한 기존 CI 개인키와 EXE 승인 개인키는 계속 사용할 수 있습니다. Tools 초기 상태와 개인키 교체는 별개입니다. 기존 키를 계속 사용한다면 새 서버에도 대응하는 공개키를 등록합니다. 개인키는 서버 웹에 업로드하지 않습니다.

CI용 소스는 IDE에서 저장하거나 수정하지 않습니다. CI가 소스를 검증하고 별도 임시 복사본에서 직접 빌드합니다. 수동 개발/IDE 빌드에는 별도 복사본을 사용합니다.

1. 명령 창 준비

Windows x64 로그인 세션의 Visual Studio x64 Native Tools 명령 프롬프트에서 새 GameWeb\tools 폴더로 이동합니다. PowerShell 7 x64, 지원되는 Node.js x64, RAD Studio classic Win64 Delphi/C++ 및 SDK, Microsoft C++/Windows SDK, Python 3, OpenSSL이 필요합니다. BDS는 실제 설치 경로로 설정합니다.

set "BDS=C:\Program Files (x86)\Embarcadero\Studio\37.0"

위 경로가 자신의 설치본과 다르면 실제 경로를 사용합니다. 이후 BAT는 같은 명령 창에서 실행합니다.

2. 새 Tools 입력 준비

순서작업결과 / 입력
1Create_Spec.bat실제 릴리스 숫자 버전, 서버 최솟값 이상의 securityVersion, 실제 도구 버전을 입력하여 tools/spec.json 생성.
2관리자 웹의 공개키·보호 정책 설정서버 보안 · 배포 운영 → 정책 편집에서 EXE 승인 공개키를 신뢰 서명자로 등록합니다. 검사 결과 정책은 검사 실패 시 작업 보류, 읽기 전용 API 저장 요구와 배포 서명 강제는 체크합니다. 영향 미리보기 → 미리본 정책 적용 후 명세 생성용 현재 정책 JSON 저장으로 받은 파일을 tools/deployment-policy.json에 저장합니다.
3Observe_Build_Inputs.bat실제 도구·SDK·라이브러리 파일 관측 → tools/observed-build-inputs.json.
4입력 검토 후 Approve_Build_Inputs.bat신뢰하는 설치본과 관측 내용을 검토한 뒤, 검토한 inputSha512를 입력합니다. tools/reviewed-build-inputs.json 생성. 과거 실행의 해시를 복사해서 사용하지 않습니다.
5CI 개인키 선택기존 CI 개인키가 있으면 그대로 사용합니다. 없을 때만 Create_CI_Key.bat 실행. EXE 승인키와 CI 키는 서로 다른 키여야 하며 소스 폴더 밖에 보관합니다.
6Export_CI_Public_Key.bat선택한 CI 개인키의 .pem 전체 경로 입력 → tools/ci-public-key.json 생성. 이 JSON으로 관리자 웹의 CI 전용 공개키 등록 실행.
7Check_Environment.bat필수 도구·소스·정책·입력 확인. 이 단계는 Windows 통합 시험 PASS가 아닙니다.
8Run_Windows_CI.bat실제 빌드·검사·실행·승인·CI 증거 서명 수행.

EXE 승인 공개키는 기존 승인 JSON의 trustedKey 공개 정보를 배열로 등록할 수 있습니다. 기존 EXE 승인 개인키와 대응하는 공개키를 사용합니다. 새 실행 파일의 승인 서명은 CI가 다시 생성하므로 과거 EXE의 승인 서명을 새 파일에 붙이지 않습니다.

생성 도구는 기존 JSON을 덮어쓰지 않습니다. 도중에 입력을 바꿔 다시 만들 때는 해당 이전 출력만 따로 보관하고 다시 실행합니다. JSON을 빈 내용이나 임의 PASS로 채우지 않습니다.

3. Windows CI 실행과 결과 위치

Run_Windows_CI.bat에서는 CI 개인키, EXE 승인 개인키 순서로 경로를 입력합니다. 두 질문 모두 폴더나 공개키 JSON이 아닌 .pem 파일까지 포함한 전체 경로입니다. BDS가 설정되지 않았다면 먼저 설치 경로를 묻습니다.

로그인 세션을 유지하고 시험용 창을 임의로 닫지 않습니다. 성공하면 화면의 CI evidence JSON: 뒤에 전체 경로가 표시됩니다. 같은 tools/ci-runs/windows-실행ID/ 폴더에 A.exe, B.exe, O.exe, 각 .approval.json, manifest.json, ci-evidence.json이 함께 생성됩니다.

실패하면 FIRST FAILED STAGE와 바로 아래 단계 로그, 해당 실행의 runner-results.json을 확인합니다. 로컬 도구 실패 때문에 서버를 다시 초기화할 필요는 없습니다. FAIL/NOT_RUN을 PASS로 바꾸거나 CI 증거를 수동으로 만들지 않습니다.

4. 관리자 웹 등록

  1. 성공한 같은 실행 폴더의 manifest.json으로 파일 업로드 전 명세 계획 등록.
  2. 같은 폴더의 A/B/O EXE와 각각의 승인 JSON을 같은 명세 ID·실행 버전으로 후보 등록.
  3. 같은 manifest.json으로 세 파일 확인 후 명세 등록 완료.
  4. 같은 폴더의 ci-evidence.json 등록.
  5. 그 A/B/O 조합 검증 → 검증한 A/B/O 조합 운영 게시.

CI가 만든 최종 EXE·승인·명세·증거를 함께 사용합니다. 이 파일을 다시 빌드하거나 수동 승인/명세 생성 도구로 재처리하지 않습니다. 서버 정책이 바뀌었다면 현재 정책으로 새 CI 실행을 준비합니다.

수동 빌드와 필수 소스

수동 IDE 빌드 최종 EXE는 GameConnect_Win64/Win64/Release/ 한 폴더에 A_난수.exe, B_난수.exe, O_난수.exe로 모입니다. 중간 DCU와 컴파일 출력은 충돌 방지를 위해 역할별로 분리합니다. 운영 등록에는 위 CI 실행 폴더의 검증된 조합을 사용합니다.

services/vendor의 WASM·라이선스, scripts/fixtures의 JSON·출처 자료, maintenance/source-manifest.json은 실행 기록이 아닌 필수 소스입니다. 삭제하지 않습니다. 동봉된 RES는 빌드 편의를 위한 생성물이며 CI는 검토된 리소스 도구로 새로 생성합니다.

실제 Windows/RAD Studio/TPM/GPU 결과는 사용자 PC의 CI 실행에서 생성됩니다. 이 초기 패키지에는 실행 완료 또는 운영 승인 상태가 없습니다.
