Game 수동 빌드 · 배포 순서

이 버전은 IDE 빌드 → EXE 승인 → 배포 명세 → 서버 검증·운영 게시로 진행합니다. ci-evidence.json 제출은 필수가 아닙니다. CI를 실행하지 않은 배포를 CI PASS 또는 하드웨어 검증 완료로 표시하지 않습니다.

1. 전체본 적용과 기존 설정

새 GameConnect_GameWeb_Completed_4-6 폴더에 전체 압축을 풉니다. GameWeb와 GameConnect_Win64는 같은 상위 폴더에 둡니다. 이 패키지에는 운영 데이터·개인키·실제 Tools JSON·실행 로그·CI 결과가 없습니다. *.example.json과 시험용 fixture는 소스 자료입니다.

기존 서버를 업그레이드할 때는 현재 운영 데이터와 서버 설정을 백업·보존하고, 이 버전의 GameWeb 소스를 모두 적용한 뒤 서버를 재시작합니다. 서버 초기화가 필요하지 않습니다. 서로 다른 버전의 services·scripts·tools 파일을 일부만 섞지 않습니다.

기존 EXE 승인 개인키와 서버의 신뢰 서명자 등록은 계속 사용합니다. 새 Tools에는 내용이 유효한 기존 spec.json을 복사할 수 있습니다. deployment-policy.json은 업데이트한 서버에서 현재 정책을 다시 내보냅니다. 이전 EXE의 승인 JSON과 이전 명세는 따로 보관하고, 아래 새 빌드에 다시 붙이지 않습니다. CI 키와 과거 CI 기록은 보존해도 되며 수동 배포에는 사용하지 않습니다. 개인키를 웹에 업로드하지 않습니다.

2. 준비와 IDE 빌드

이 경로에는 Windows, IDE에서 사용할 수 있는 RAD Studio classic Win64 Delphi/C++·SDK, Node.js LTS, Windows PowerShell 5.1 이상이 필요합니다. Node는 현재 패키지에서 지원하는 버전(22.22.2 이상 / 24.15.0 이상 / 26 이상)을 사용합니다. CI용 PowerShell 7·MSVC·OpenSSL·검토 입력 기록은 수동 배포의 선행 조건이 아닙니다.

서버 의존성은 GameWeb/package.json과 package-lock.json에 맞춰 실제 서버의 OS·Node 환경에 설치합니다. 다른 PC나 다른 OS에서 만든 node_modules를 그대로 복사하지 않습니다. better-sqlite3 같은 네이티브 의존성도 해당 환경에서 사용할 수 있어야 합니다. 이 설치와 패키지의 services/scripts 원본 복원은 별개의 작업입니다.

명령 프롬프트에서 새 GameWeb\tools로 이동하고 실제 RAD Studio 설치 경로를 설정합니다.

set "BDS=C:\Program Files (x86)\Embarcadero\Studio\37.0"
call Prepare_ImGui.bat

Prepare_ImGui.bat이 성공하면 Delphi IDE에서 GameLauncher.dproj, GameConnect.dproj, GameOverlay.dproj를 Win64 / Release로 빌드합니다. ImGui 준비가 실패하면 표시된 네이티브 빌드 로그부터 확인합니다. 이 도구는 ImGui C++ 브리지만 준비하며 Delphi 명령줄 빌드나 Windows CI를 실행하지 않습니다.

최종 EXE는 GameConnect_Win64\bin 한 폴더에 모입니다. Debug와 Release 모두 이 폴더에 모이며 이름은 A_Release_난수.exe, B_Release_난수.exe, O_Release_난수.exe 또는 역할_Debug_난수.exe입니다. 운영 게시에는 Release만 선택합니다. 이름을 바꾸어도 EXE 내부 Debug/Release 표시는 바뀌지 않습니다. 여러 빌드가 있으면 이번 빌드의 세 파일을 선택합니다. 중간 DCU와 컴파일 출력은 충돌 방지를 위해 내부적으로 역할별 분리합니다.

3. 최종 파일 승인과 명세

순서작업결과 / 입력
1Create_Spec.battools/spec.json 생성. 실제 A/B/O 숫자 버전(예: 1.0.0), 서버 최솟값 이상의 securityVersion, 실제 컴파일러·SDK·ImGui 버전을 입력합니다. 기존 spec이 맞으면 다시 생성하지 않습니다.
2Create_Approval.bat이번 빌드의 A, B, O를 각각 선택하고 같은 릴리스 버전과 기존 EXE 승인 개인키를 사용합니다. 각 *.approval.json은 BAT와 같은 Tools 폴더에 생성됩니다. O는 이 과정에서 PE 예외 테이블 정리로 EXE 바이트가 바뀔 수 있습니다.
3Check_Approval.bat정리·승인을 마친 A/B/O 각각과 대응하는 새 approval JSON을 선택하여 서명·해시·구분·버전을 확인합니다. 개인키가 필요하지 않습니다.
4관리자 웹에서 현재 배포 정책 내보내기EXE 승인 공개키가 신뢰 서명자로 등록되어 있는지 확인합니다. 신규 키인 경우 Check_Approval에서 확인한 공개키 배열을 정책에 추가하고 영향 미리보기 → 적용합니다. 그 뒤 명세 생성용 현재 정책 JSON 저장으로 tools/deployment-policy.json을 저장합니다. 기존 서명·무결성 정책을 해제할 필요가 없습니다.
5Create_Release_Manifest.bat승인·점검을 마친 동일한 최종 A/B/O 경로를 차례로 입력합니다. tools/release-manifest.json과 패키지 출처 기록 사본인 tools/source-manifest.json 생성.
6Check_Manual_Release.batA EXE·A approval JSON, B EXE·B approval JSON, O EXE·O approval JSON 순서로 선택합니다. 소스 목록의 모든 SHA-512·누락·로컬 JS 참조, 실제 EXE 내부 빌드 구성, 서명·역할·버전·현재 해시·정책·명세를 읽기전용 점검합니다. 결과는 BAT 옆 manual-release-check-실행ID.json에 저장합니다.

명세는 Create_Approval / Check_Approval 다음에 만듭니다. 명세 생성 뒤 EXE를 재빌드·수정하거나 O를 다시 정리하면 해시가 달라집니다. 바뀐 파일을 다시 승인·점검하고 새 명세를 만든 뒤 하나의 조합으로 등록합니다.

생성 도구는 기존 JSON을 자동으로 덮어쓰지 않습니다. 새 릴리스를 만들 때 이전 승인·명세를 별도 폴더에 보관한 뒤 새로 생성합니다. 소스 패키지를 바꾸었다면 이전 tools/source-manifest.json도 이전 명세와 함께 보관하여 새 패키지 기록으로 생성합니다. 빈 파일이나 임의의 해시/PASS로 대체하지 않습니다.

source-manifest.json은 배포에 참조한 소스 패키지의 기록입니다. 수동 점검은 목록에 있는 모든 파일의 실제 SHA-512를 대조하고 검사 종료 시 다시 확인합니다. 누락·변경·경로 탈출·심볼릭 링크/연결·Windows 경로 중복은 거절합니다. JS 문법과 정적으로 찾은 로컬 require 참조도 검사합니다. 목록에 없는 파일 전체를 검증하거나 기록 자체의 진위를 인증하는 것은 아니며, IDE가 이 소스를 실제로 컴파일했다는 인과관계도 증명하지 않습니다. EXE·승인·정책·명세의 현재 바이트와 서명·해시 정합성은 별도로 검사합니다.

MANUAL_SOURCE_HASH_MISMATCH이면 표시된 파일과 배포 출처 기록이 다릅니다. 실수로 바뀐 파일은 해당 패키지의 원본으로 복원합니다. IDE가 프로젝트를 저장했거나 의도적으로 소스를 수정했다면 변경 내용을 독립적으로 검토하고 그 변경을 반영한 새 소스 기록·배포 명세를 준비해야 합니다. 서버 초기화나 기준값 삭제로 해결하지 않습니다. 이 도구는 기준 해시를 자동 갱신하지 않습니다.

선택 점검과 오류 위치

명세를 만들기 전에 승인된 파일만 먼저 확인하려면 Check_Manual_Release.bat /pre-manifest를 사용합니다. 이 단계는 명세를 만들거나 서버에 등록하지 않습니다. 명세 생성 뒤에는 옵션 없이 다시 실행해 전체 파일 조합을 점검합니다. 기존 Check_Release_Manifest.bat도 명세 일치 점검용으로 유지합니다.

이미 독립 검토한 tools/reviewed-build-inputs.json과 현재 컴파일러·SDK·RTL·ImGui 브리지·Node 입력까지 대조하려면 Check_Manual_Release.bat /verify-build-inputs를 사용하고 실제 RAD Studio 경로를 BDS에 설정합니다. 저장된 관측 JSON을 신뢰하는 대신 현재 파일을 다시 읽어 검토 기록과 비교합니다. 새 검토 기록을 생성·승인하거나 컴파일러를 실행하지 않습니다. 옵션을 생략하면 이 항목은 NOT_CHECKED로 남으며, 사용해도 도구의 진품 여부나 과거 IDE 빌드의 실제 입력을 증명하지는 않습니다. 이 선택 검사는 CI 선행 조건이 아닙니다.

실패 화면과 결과 JSON에 첫 실패 stage / code / file / action을 남깁니다. MANUAL_LOCAL_MODULE_MISSING이면 가리키는 로컬 파일을 완전한 같은 버전 패키지에서 복원하며, npm 설치나 서버 초기화로 대체하지 않습니다. Debug 또는 구성 표시가 없는 예전 EXE는 현재 프로젝트의 Win64 Release로 다시 빌드합니다. 서명 후 파일이 바뀌었으면 새 승인과 새 명세가 필요합니다.

실제 Windows 동작을 별도로 확인하려면 다음 선택 절차를 사용합니다. 운영 게시의 필수 단계는 아닙니다.

  1. RAD Studio IDE에서 GameConnect_Win64/tests/manual-ide/ManualNativeTests.groupproj를 열어 Win64 Release로 Build All 합니다. 시험 EXE는 tests/manual-ide/bin에 생성됩니다. C++ SDK ABI 대조도 하려면 같은 폴더의 NativeAbiSdkProbe.vcxproj를 Visual Studio IDE에서 Release x64로 빌드합니다.
  2. Run_Manual_Windows_Tests.bat를 실행하고 probe 폴더를 선택합니다. A/B/O 실행까지 확인하려면 YES를 입력하고 실제 최종 Release 파일 세 개와 버전을 선택합니다. 이 경우에만 새 임시 localhost 서버를 사용하며, 운영 서버·승인 개인키를 입력하지 않습니다.
  3. BAT 옆 manual-실행ID-results.json과 실행 폴더의 로그를 확인합니다. 이전 manual-실행ID-inputs.json 경로를 BAT에 전달하면 같은 선택값을 재사용할 수 있습니다. 없는 probe나 선택하지 않은 단계는 NOT_RUN으로 남습니다.

프로브의 IDE 설정과 별도 GPU 장애 브리지 준비는 Manual_Windows_Tests.html에서 확인합니다. 다음 추가 단계도 실제 빌드된 시험 파일이 있을 때 실행됩니다.

별도 명령줄 probe 빌드 BAT는 이전의 해당 출력 파일을 먼저 제거하고 새 EXE/DLL이 생성됐는지 확인합니다. dcc64가 종료 코드 0을 반환해도 새 파일이 없으면 PROBE_NO_FRESH_OUTPUT으로 중단합니다. Trial 등 현재 설치가 명령줄 컴파일을 허용하지 않으면 위 IDE 그룹 프로젝트로 빌드합니다. 이전 출력 재사용이나 라이선스 제한 우회는 하지 않습니다.

단계확인 범위
blake3-parallel병렬 BLAKE3 hash/keyed/derive 및 XOF 결과를 포함한 probe 출력을 고정된 독립 구현과 비교합니다. 빌드·실행 환경 자체의 인증은 아닙니다.
handoff-kdf독립 KDF 벡터, seed·transcript의 목적 분리, 입력 길이 경계, 빌려온 입력 버퍼 보존을 검사합니다.
module-generation / thread-inventory시험용 DLL의 실제 load/unload 감지와 측정 수명, 스레드 열거의 핸들 정리·취소·미확인 상태를 검사합니다. 정상 모듈인지 알 수 없는 스레드를 곧바로 악성으로 판정하거나 임의로 종료하지 않습니다.
independent-pe / independent-crcPython 독립 참조와 Delphi probe의 PE 수용/거절, 파일·코드·Export SHA-512/CRC64를 비교합니다. 별도 CRC 단계는 9종 기본 계산·상수/테이블·페이지 프레임을 대조합니다. Python이 없으면 해당 독립 비교는 NOT_RUN입니다. nativeAuxiliaryCrcCompared:false가 표시되는 PE 보조 CRC 영역의 네이티브 대조까지 완료한 것으로 보지 않습니다.
overlay-privacy상태 분류 계약과 Windows의 실제 자체 D3D11 창에서 캡처 보호 켜기/끄기 및 Set/Get 결과를 검사합니다. 미지원·읽기 불가·monitor-only는 PARTIAL로 남습니다. 성공해도 API 적용·읽기 확인이며 모든 외부 캡처 도구 차단을 증명하지 않습니다.
device-signals기본 실행은 파서·digest 계약과 수집 미요청 경로만 검사합니다. 별도 하드웨어 질문에 YES를 선택한 경우에만 DeviceSignalsProbe.exe --collect-hardware로 현재 PC의 저장장치/NIC 진단을 수집합니다. 미지원·권한 부족·일부 장치 실패는 UNAVAILABLE/PARTIAL이며 원본 시리얼·MAC 대신 범위가 제한된 digest·개수·상태만 출력합니다.

디스크/NIC 질문의 기본값은 NO입니다. 입력 JSON을 직접 재사용할 때도 collectHardwareSignals:true가 있어야 수집합니다. 이 진단은 TPM 증명이나 조작 불가능한 HWID가 아니며 기존 라이선스 장치 식별을 대체하지 않습니다. 운영 A/B/O의 수집도 서버 정책 deviceSignalsRequested의 기본값 false를 유지하며 인증된 요청에서 별도로 정합니다. 실제 TPM 시험용 DeviceIdentityProbe는 기본 수동 실행 도구가 자동 실행하지 않습니다.

각 단계의 PASS는 그 단계에서 실행한 검사만 뜻합니다. 누락·미선택은 NOT_RUN, 일부 검사 생략은 PARTIAL, 실제 오류·입력 변경은 FAIL입니다. 전체 결과의 INCOMPLETE는 미실행 또는 부분 실행 항목이 남았다는 뜻이며 운영 게시를 자동 차단하지 않습니다. 이 안내나 동봉된 시험 소스가 현재 PC의 Windows 시험 통과를 의미하지는 않습니다.

이 도구는 PowerShell 7 x64에서 이미 빌드된 파일만 실행하며 dcc64/MSBuild나 CI 증거 생성을 실행하지 않습니다. A/B/O 통합 시험은 OpenSSL이 추가로 필요합니다. GPU 장애 probe는 별도 fault bridge 빌드가 필요하므로 없으면 NOT_RUN입니다. 결과의 MANUAL_EXECUTION은 실행한 항목에만 해당하며 CI·컴파일 출처·하드웨어 인증·운영 게시 승인이 아닙니다. 실제 TPM 장치 증명, DPI·다중 모니터, GPU 드라이버 소실, RDP 전환은 별도로 확인해야 합니다. 파일 점검 PASS는 Windows 실행 시험 PASS가 아닙니다.

A/B/O 실행을 선택하여 Windows x64에서 세 입력이 확보된 경우, BAT 옆에 업로드용 manual-실행ID-results-verification.json도 생성됩니다. 콘솔의 관리자 업로드 경로 또는 로컬 결과의 publicVerificationFile을 확인하세요. 파일 경로·로그·키를 포함한 전체 로컬 결과 대신 이 공개 요약 JSON만 사용합니다. 실패·부분 실행·미실행 단계도 그대로 기록하며, 파일 생성 자체는 시험 통과가 아닙니다.

관리자 웹 서버 복구 · 장치 · 저장소 → 수동 Windows 시험 기록에서 해당 32KiB 이하 JSON을 선택해 등록할 수 있습니다. 관리자 권한·유효한 세션·최근 재인증과 CSRF 검증이 필요합니다. 서버에 같은 최종 A/B/O와 같은 소스 기록을 묶은 명세가 먼저 REGISTERED로 등록되어 있어야 합니다. 서버는 소스 명세 SHA-512, 세 역할의 EXE SHA-512, 각 후보의 배포 명세 ID가 모두 같은 등록 명세에 속하는지 확인하며 다른 명세의 파일을 섞으면 거절합니다. 현재 운영 조합과 정확히 일치하는 기록만 상태에 연결합니다. 등록 결과는 OPERATOR_RECORDED이며 성공 표시도 PASS_REPORTED로 구분합니다. CI 서명·실제 IDE 컴파일 출처·하드웨어 증명·실행 또는 게시 승인으로 사용하지 않습니다. 이 등록은 선택 사항이며 CI를 다시 요구하는 단계가 아닙니다.

4. 관리자 웹 등록과 운영 게시

  1. tools/release-manifest.json으로 파일 업로드 전 명세 계획 등록.
  2. 해당 명세 ID를 사용하여 동일한 최종 A/B/O EXE와 각 새 approval JSON을 후보 등록. 역할과 버전은 승인 생성 때와 동일하게 입력합니다.
  3. 같은 명세로 세 파일 확인 후 명세 등록 완료하여 REGISTERED 상태 확인.
  4. 그 A/B/O 조합 검증 → 검증한 A/B/O 조합 운영 게시.

CI 증거 JSON 업로드 단계는 없습니다. 서버는 명세 등록 상태, 최종 해시, EXE 승인 서명, 역할·버전, 배포 정책 등 기존 검증을 계속 수행합니다. 운영자가 별도로 시험 기록 또는 빌드별 검사 규격을 필수로 설정한 경우 해당 조건은 그대로 적용되므로, 표시되는 실제 조건을 확인합니다. 시험을 수행하지 않았다면 PASS로 기록하지 않습니다.

정책이나 최종 파일을 바꾸면 새 조합에 맞는 정책 내보내기·승인·명세가 필요할 수 있습니다. 로컬 도구 오류 때문에 서버나 키를 초기화할 필요는 없습니다.

선택 사항: Windows CI와 필수 소스

CI 스크립트와 과거 증거 검증 기능은 보존되어 있습니다. CI를 사용하려는 경우에만 명령줄 컴파일을 지원하는 환경에서 기존 입력 검토·CI 키·Windows 시험 절차를 수행합니다. 일반 운영 게시 화면에는 CI 증거 업로드 항목이 없습니다. 기존 CI API와 기록 검증은 호환성을 위해 보존합니다. CI 공개키 생성 자체는 시험 실행 또는 CI PASS를 의미하지 않습니다.

services/vendor의 WASM·라이선스, scripts/fixtures의 JSON·출처 자료, maintenance/source-manifest.json은 실행 기록이 아닌 필수 소스입니다. 삭제하지 않습니다. 동봉 RES는 빌드용 리소스이며 빌드 시 정상 리소스 생성 절차를 유지합니다.

이 패키지에는 생성된 승인·운영 게시 상태가 없습니다. 수동 배포의 서버 승인과 자동화된 Windows CI 시험 결과는 구분하여 기록합니다.
