Game 배포 순서

이 압축의 GameConnect_Win64와 GameWeb를 같은 상위 폴더에 풉니다. 이전 패치 파일을 섞지 않습니다. 기존 서버의 운영 데이터·환경 설정·키는 백업하고 보존합니다.

새 폴더를 CI 전용으로 사용하세요. CI 실행 전 이 폴더의 프로젝트를 IDE에서 저장하거나 소스를 수정하지 않습니다. CI가 검증한 소스를 별도 작업 폴더에 복사하여 직접 빌드합니다. IDE에서 개발할 때는 별도 복사본을 사용합니다.

GameConnectResources.res, GameLauncherResources.res, GameOverlayResources.res는 빌드 생성물입니다. 편의상 동봉하지만 소스 해시 비교·CI 복사 대상에서 제외합니다. 원본 .rc·.manifest·아이콘·라이선스는 계속 해시로 검증하며, CI는 검토된 brcc32.exe로 리소스를 새로 생성한 뒤 검사합니다.

서버 초기화는 로컬 소스 해시 오류의 해결 단계가 아닙니다. 서버를 새로 구성했다면 기존 개인키를 보존하고 EXE 승인 공개키와 CI 공개키를 새 서버에 다시 등록한 뒤, 그 서버의 현재 배포 정책을 새로 내보내세요. 예전 서버의 정책 JSON·배포 명세·증빙을 새 실행 결과와 섞지 않습니다.

운영 게시에는 실제 Windows 빌드·API 검사·A→B→O 실행 검증의 CI 서명이 필요합니다. IDE 빌드 성공이나 수동 PASS 입력만으로 이 조건을 충족하지 않습니다.

1. 도구와 입력 준비

Windows x64 로그인 세션에서 PowerShell 7 x64, 프로젝트가 지원하는 Node.js x64, RAD Studio classic Win64 도구, Microsoft C++/Windows SDK, Python 3 및 OpenSSL을 준비합니다. Python은 서버의 SQLite 네이티브 모듈 빌드에 필요합니다. C++ Build Tools의 x64 Native Tools 명령 프롬프트를 사용하고 BDS를 실제 RAD Studio 경로로 설정합니다. RAD Studio SDK 헤더와 MSVC SDK는 각각 필요합니다.

순서실행 / 입력결과
1Create_Spec.battools/spec.json. releaseName은 1.0.0 같은 실제 A/B/O 숫자 버전, securityVersion은 서버 최솟값 이상.
2관리자 웹에서 현재 배포 정책 내보내기tools/deployment-policy.json. 사용할 EXE 승인 공개키가 이 정책에 등록되어 있어야 합니다.
3Observe_Build_Inputs.battools/observed-build-inputs.json. 도구·SDK·라이브러리의 실제 파일 기록.
4신뢰하는 설치본과 입력을 검토한 후 Approve_Build_Inputs.bat검토한 inputSha512를 직접 입력하여 tools/reviewed-build-inputs.json 생성. 관측값을 자동으로 승인하지 않습니다.
5Create_CI_Key.batEXE 승인키와 다른 CI 전용 Ed25519 키 생성. 기존 CI 키를 사용할 때는 생성 단계를 생략합니다. 개인키는 소스 폴더 밖에 보관합니다.
6Export_CI_Public_Key.battools/ci-public-key.json. 관리자 웹의 CI 공개키 등록에 사용할 공개 정보만 포함합니다.
7Check_Environment.bat필수 도구·입력·소스 누락 확인. 준비 검사는 Windows 통합 시험 PASS가 아닙니다.

생성 도구는 기존 JSON·키를 덮어쓰지 않습니다. 새 배포를 준비할 때는 이전 배포의 파일을 별도로 보관합니다. 정책·소스·도구가 바뀌면 그 변경에 맞게 입력 기록과 증빙을 새로 준비합니다.

2. 실제 빌드와 실행 검증

  1. Run_Windows_CI.bat을 실행하고 BDS, 기존 EXE 승인 개인키, CI 개인키 경로를 입력합니다.
  2. 도구가 새 tools/ci-runs/<실행 ID> 폴더를 만들고 별도 복사본에서 A/B/O 빌드, 정규화, 승인, 네이티브 검사, 실제 실행과 종료를 검증합니다. 창이 나타나는 통합 시험이므로 로그인 세션을 유지합니다.
  3. 실패하면 화면에 나온 단계와 해당 실행 폴더의 runner-results.json, logs를 확인합니다. FAIL/NOT_RUN을 PASS로 수정하지 않습니다.
  4. 성공한 폴더를 Check_CI_Output.bat으로 검사합니다. 로컬 서명·파일 일치 검사 후에도 서버에 공개키와 증빙을 등록해야 합니다.

CI가 생성한 명세와 A/B/O를 그대로 사용합니다. 이 EXE를 다시 빌드·정규화하거나 수동 Create_Release_Manifest.bat으로 다른 명세를 만들면 기존 CI 서명과의 연결이 바뀝니다.

3. 관리자 웹 등록

  1. tools/ci-public-key.json으로 CI 공개키를 등록합니다. 개인키는 업로드하지 않습니다.
  2. 성공한 같은 CI 실행 폴더의 manifest.json을 계획 등록합니다.
  3. 같은 폴더의 A.exe, B.exe, O.exe와 각각 A.approval.json, B.approval.json, O.approval.json을 같은 명세 ID·실행 버전으로 후보 등록합니다.
  4. 명세 등록을 완료하고 같은 폴더의 ci-evidence.json을 등록합니다. 필요한 빌드별 정책을 적용할 때는 같은 실행에서 생성된 mitigation-*.json도 해당 화면에서 등록합니다.
  5. 해당 A/B/O를 선택해 조합을 다시 검증하고 운영 게시합니다. 서버 정책 revision이 달라졌다면 현재 정책으로 CI를 다시 실행합니다.

도구 구분

Prepare_ImGui.bat는 C++ 객체 준비, Create_Approval.bat와 Check_Approval.bat는 개별 EXE 승인 도구입니다. Test_Native_*.bat·Test_Server_*.bat는 개별 진단입니다. 이 도구들만 실행해도 CI 게시 증빙이 만들어지는 것은 아닙니다. TLS·저장소·복구 BAT는 해당 운영 작업이 필요할 때만 별도로 실행합니다.

SECURITY_CI_EVIDENCE_REQUIRED: 같은 명세의 유효한 CI 서명 및 3개 PASS를 확인합니다.
SECURITY_PUBLICATION_REQUIREMENTS_REQUIRED: 필수 게시 조건을 끄거나 최소 보안 버전을 1 미만으로 저장한 요청입니다. 명세·증빙을 준비해 게시합니다.

이 패키지의 정적·Node 검사는 실제 Windows/RAD Studio/TPM/GPU 실행의 대체 증빙이 아닙니다. 실제 결과는 사용자 Windows CI 실행에서 생성됩니다.
