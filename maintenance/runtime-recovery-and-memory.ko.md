# 등록 파일 검사·연산 결과 재조회·민감 버퍼 변경

2026-11-01 (Asia/Seoul). 서버 배포와 A/B/O 소스 적용 범위를 구분합니다.

## 1. 등록 파일 보안 검사

관리자 웹의 **서버 보안 · 배포 운영 → 등록 파일 보안 검사**에서 사용합니다. 별도 설정이나 새 서비스는 필요하지 않습니다.

- 파일 읽기·해시·PE/CFG 검사와 A 공개 검증 키 추출을 일회성 작업 스레드로 옮겼습니다.
- 동시 작업은 1개이며 대기열을 만들지 않습니다. 10초 제한 시점에 중단을 요청하고 실제 스레드 종료까지 기다립니다. 파일당 64MiB, 전체 128MiB로 제한하며 순서대로 읽습니다.
- 접속 종료, 관리자 세션 만료, 서버 종료 시 작업을 취소합니다. 작업 스레드가 종료되기 전에는 다음 작업을 시작하지 않습니다.
- 검사 도중 활성 파일·정책·운영 revision이 바뀌면 결과를 폐기합니다. 무관한 실행 세션의 heartbeat는 검사를 무효화하지 않습니다.
- 작업 스레드에는 개인 서명 키와 운영 환경 변수를 넘기지 않습니다. 승인 서명 검증과 A 발급 준비 서명 확인은 현재 권한 상태를 확인한 주 처리 흐름에서 수행합니다.
- 이는 CPU 작업 분리이며 별도 OS 보안 경계가 아닙니다. JavaScript heap 제한만으로 Buffer 메모리가 제한되는 것도 아니므로 파일 크기 한도를 별도로 유지합니다.

검사 결과는 배포 승인이나 실제 Windows 실행·게시자 신뢰 검증을 대신하지 않습니다. CFG 표시 비트만 수정하거나 CFG 요구를 자동 해제하지 않습니다.

## 2. 서버 연산의 결과만 재조회

공통 `Cozy.ServerOperations` 호출 경로에 `policy/result` 동작을 연결했습니다. 서버 연산을 다시 실행하는 요청과 구분합니다. 기존 challenge/invoke 규격은 유지하며 result 규격을 추가했습니다.

- 실행 전에 제한된 결과 보관 공간을 예약합니다. 공간이 없으면 연산을 시작하지 않습니다.
- 결과는 최대 30초 동안 메모리에 보관합니다. 동일 요청 ID의 재사용을 막는 시도 기록은 최대 5분, 전체 최대 2,048개입니다.
- 원래 서명된 요청의 역할·세션·기기·요청 ID·인수 해시·서명·토큰 연결과 현재 정책·파일·공개키 상태를 검사합니다.
- 세션 종료, 차단, 정책 변경, 라이선스 만료 또는 현재 무결성 권한 상실 시 결과 조회도 거부합니다. 결과 조회는 권한 수명을 늘리지 않습니다.
- 제한된 통신 유실 오류에서만 공통 클라이언트가 결과 조회를 한 번 시도합니다. 정상적인 거절이나 취소는 재실행하지 않습니다.
- 서버 재시작·배포로 메모리 결과가 사라지면 조회에 실패합니다. 저장소를 이용한 영구적인 exactly-once 실행이나 부작용 있는 외부 업무의 중복 방지를 제공하는 기능은 아닙니다.

현재 사용자 정의 연산은 제한된 순수 Int32 정책 함수입니다. 실제 제품 업무 함수는 별도 함수·입출력·호출 위치 명세가 필요합니다.

## 3. A/B/O 민감 데이터 사본과 수명 축소

`Cozy.Api.Contracts`, `Cozy.JsonEnvelope`, `Cozy.Transport`의 공통 경로를 변경했습니다.

- UTF-8 변환 결과를 최종 소유 바이트 배열에 직접 기록하고 내부적으로 소유권을 넘깁니다. 임시 바이트 배열을 별도 할당 영역으로 다시 복사하는 단계를 제거했습니다.
- JSON 봉투 조립 시 본문 전체를 위한 두 번째 소유 버퍼를 없앴습니다.
- 네트워크 대기 전에 사용이 끝난 직렬화·Base64 임시 값과 JSON 트리를 정리합니다. 검증된 복호화 이후에는 사용이 끝난 전송 키를 바로 해제합니다.
- 크기 제한, 취소, 오류 시 정리와 공유 핸들 무효화 규칙을 유지합니다. Delphi의 공개 인덱스 기반 Encoding API를 사용합니다.

JSON/RTL 내부의 모든 사본, 운영체제 캐시·덤프·페이지 파일의 흔적까지 제거했다는 의미는 아닙니다. 클라이언트가 사용하는 일시적인 세션 자료와 공개 검증 정보는 실행 중 메모리에 존재할 수 있습니다. 서버 개인키를 클라이언트에 추가하지 않았습니다.

## 적용 범위

서버 변경은 Railway 배포 후 적용됩니다. 클라이언트 변경은 A/B/O를 기존 빌드 방식으로 다시 빌드하고 최종 파일 승인·명세·등록·게시한 뒤 새 A를 발급해야 적용됩니다. 이미 발급한 EXE는 자동으로 바뀌지 않습니다. 새 CI나 Windows/Delphi 환경 설치 절차는 추가하지 않았습니다.

검증 결과와 실제 배포 상태는 풀 소스의 `tools/package-check/runtime-next-status.json`과 `deployment-status.json`을 확인하세요. 실제 Windows 컴파일·A→B→O 실행 시험은 이 작업 환경에서 수행하지 않았습니다.
