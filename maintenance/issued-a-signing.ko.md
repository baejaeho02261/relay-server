# 최종 발급 A의 서명 연결

서버는 승인된 A 템플릿과 정확한 발급 설정을 함께 서명합니다. A는 네트워크 주소·TLS 핀·발급 ID를 사용하기 **전에** 자신의 파일에서 서명을 검증합니다. 개인키는 서버의 `DESKTOP_ISSUED_A_SIGNING_PRIVATE_KEY_B64` 변수에만 설정하며, A에는 그 키에 대응하는 공개 검증 키만 빌드합니다. 이 공개키는 비밀정보가 아닙니다.

이 기능은 애플리케이션의 발급 설정 인증입니다. Windows Authenticode, 게시자 인증서 또는 실제 Windows 실행 시험을 대신하지 않습니다. A/B/O의 기존 배포 승인·명세·일회용 소비·PC 정책·서버 인증은 유지됩니다. CI 기능은 사용하지 않습니다.

## 적용 순서

1. 전용 RSA 2048, 공개 지수 65537 개인키를 서버 변수 `DESKTOP_ISSUED_A_SIGNING_PRIVATE_KEY_B64`에 설정합니다. 값은 PKCS8 PEM 전체 바이트의 표준 Base64입니다. 전송용 TLS/RSA 키 또는 EXE 배포 승인 키를 재사용하면 목적 충돌로 거절합니다.
2. 같은 키의 **공개키만** `Cozy.Source/Cozy.Security/Cozy.IssuedA.TrustAnchor.inc`에 반영한 최신 전체 소스로 A를 Win64 Release 빌드합니다. 전체 소스에 포함된 공개키와 실제 서버 변수의 키 ID가 일치해야 합니다. 서버 변수 설정이 승인되지 않았거나 누락된 상태를 설정 완료로 취급하지 않습니다.
3. A/B/O의 서버 정책 연결, 최종 파일 승인, 최종 배포 명세 등록을 기존 절차대로 수행합니다. 서버 보안 · 배포 운영에서 새 A/B/O 후보 조합을 검증합니다.
4. 조합 검증은 A의 실제 PE 읽기 전용 섹션에서 공개키를 읽고 서버의 전용 키와 비교한 뒤 서명·검증 시험을 수행합니다. 새 검증기가 없는 A는 `ISSUED_A_BUILD_UPGRADE_REQUIRED`, 개인키가 없으면 `ISSUED_A_SIGNING_KEY_NOT_CONFIGURED`, 서로 다르면 `ISSUED_A_SIGNING_KEY_MISMATCH`로 거절합니다.
5. 게시 후 기존 **일회용 A 발급** 버튼을 사용합니다. 서버는 개인화된 최종 파일을 서명하고 재검증한 뒤, 그 최종 해시와 서명 봉투를 발급 기록에 함께 저장합니다. 다운로드는 저장한 봉투를 그대로 사용하므로 다운로드마다 새 서명이나 새 설정이 만들어지지 않습니다.
6. 새 최종 발급 A로 실제 Windows 실행·종료·일회용 재실행 시험을 수행합니다. Linux 소스 검사와 Node 암호학 시험은 이 실제 실행 결과를 만들지 않습니다.

이 변경만으로 이미 빌드한 구형 A에 검증기가 추가되지는 않습니다. 구형 unsigned V3 발급 기록은 읽기·이력 보존을 위해 유지하지만 새 다운로드와 미사용 A의 새 실행에는 서명을 요구합니다. 기존에 소비된 세션은 기존 서버 권한·만료·폐기 규칙을 계속 적용합니다. 오래된 비 V3 레거시 템플릿의 기존 발급 형식은 별도 경로로 유지합니다. 새 공개키 앵커가 있는 A를 레거시 형식으로 발급하려 하면 거절합니다.

## 공개키 도구

`tools/security/peace.issued-a-signing-key.js`는 개인키를 출력하지 않습니다. 모든 파일 경로는 절대 경로이고, 출력 파일은 기존 파일을 덮어쓰지 않습니다.

- `--action generate --private-key-file <소스 밖 새 PEM 경로> --public-json-out <새 공개 JSON 경로> --include-out <새 include 경로>`: 전용 키와 공개 산출물을 생성합니다. 개인키 파일은 소스 패키지 밖에 두고 서버에만 비밀로 전달해야 합니다. Windows에서는 새 빈 임시 디렉터리의 ACL을 먼저 제한한 뒤 그 안에 개인키 파일을 만듭니다. 제한된 파일 ACL을 유지하는 create-only 하드 링크로 게시하며, 이를 지원하지 않는 파일시스템에서는 실패합니다. 실패하면 해당 작업이 만든 파일만 정리합니다.
- `--action export --private-key-file <외부 PEM 경로> --public-json-out <새 공개 JSON 경로> --include-out <새 include 경로>`: 기존 키의 공개 정보만 내보냅니다.
- `--action include --public-json-file <공개 JSON 경로> --include-out <새 include 경로>`: 공개 JSON만으로 Pascal include를 생성합니다. 생성한 내용을 확인한 뒤 기존 `Cozy.IssuedA.TrustAnchor.inc`를 교체하고 A를 다시 빌드합니다.

키 회전 시 새 공개키를 포함한 새 A 템플릿을 승인·게시해야 합니다. 이미 서명한 발급 파일은 저장된 봉투와 기존 템플릿 공개키로 검증되며 새 개인키로 다시 서명되지 않습니다. 이전 A의 실행을 폐기하려면 기존 배포 조합·파일 폐기 정책을 사용합니다. 단순히 서버 개인키를 변경하는 것은 기존 공개 서명을 무효화하지 않습니다.

## 파일 규격

최종 파일은 `승인된 템플릿 || V3 공개 설정 || 184바이트 헤더 || RSA 서명 256바이트 || 13바이트 footer`입니다. 공개 설정의 상한은 8,192바이트이며, **최종 파일 전체**는 기존 무결성 검사와 동일하게 64MiB 이하여야 합니다. 게시 준비 검사는 설정·서명 공간 8,645바이트를 미리 예약합니다. Footer는 정확히 ASCII `COZYA4SIGNED!`입니다.

| 헤더 위치 | 길이 | 값 |
| --- | --- | --- |
| 0 | 16 | ASCII `COZY-ISSUED-A-V1` (NUL 없음) |
| 16 | 4 | 템플릿 길이, little endian |
| 20 | 4 | 공개 설정 길이, little endian |
| 24 | 32 | 공개 CNG RSA blob의 SHA-256 |
| 56 | 64 | 템플릿 전체 바이트 SHA-512 |
| 120 | 64 | 공개 설정 전체 바이트 SHA-512 |

서명은 헤더 전체의 SHA-256에 대한 RSA PKCS#1 v1.5입니다. 서명 자체를 포함한 파일 해시를 서명 입력으로 다시 넣지 않으므로 순환 해시가 없습니다. 최종 파일 SHA-512는 서명 완료 후 서버 발급 기록에 저장합니다.

공개키 앵커는 읽기 전용·비폐기 PE 섹션의 331바이트 상수입니다: ASCII `COZYAISSUERKEY1!` 16바이트, 키 ID 32바이트, Windows CNG `RSAPUBLICBLOB` 283바이트입니다. 앵커의 RSA 2048·지수 65537·키 ID를 검사하고 유효한 앵커가 정확히 하나여야 합니다. 설정이나 footer가 새 공개키를 선택하게 하지 않습니다. 외부 도구가 최종 파일을 검증할 때도 별도로 신뢰한 템플릿 해시와 키 ID를 지정해야 하며, 파일에 들어 있는 임의의 키만으로 신뢰를 선언하지 않습니다.

## 검증 범위

- Node 시험: 템플릿·설정·길이·키 ID·서명·footer 변경, 잘림·추가 바이트, 키 불일치, 중복·쓰기 가능·파일 끝에 덧붙인 앵커 거절.
- 실제 bootstrap 저장소 시험: 최종 서명 A 발급·반복 다운로드, 기존 두 키 소유 증명·관리자 승인·일회용 소비·서버 재시작 저장 검증.
- Native 시험 소스: `Cozy.Tests/Cozy.Security/Cozy.IssuedASignatureProbe.dpr`가 Windows CNG와 실제 파일 읽기로 동일 공개 벡터·변조·잘림·파일 위치 복원을 검사합니다. 실행하지 않은 환경은 NOT_RUN입니다.
- 공개키를 가진 로컬 실행 코드 전체가 공격자에 의해 교체되는 상황까지 자체 검사만으로 막는다는 보장은 하지 않습니다. 배포 승인, 서버 측 실행 권한, 파일 해시 결합과 Windows 플랫폼 보안은 계속 필요합니다.
