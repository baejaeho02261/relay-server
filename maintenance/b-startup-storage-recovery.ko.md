# B 다운로드 복구와 저장공간 진단

2026-11-18 KST 수정. 기존 B 갤러리 디자인과 A/B/O 인증·종료 정책을 유지합니다.

## 확인한 실행 기록

A의 최초 파일·코드·CRC·API 포인터 측정은 서버 등록 기준과 일치했습니다. 서버는 첫 다운로드 조각의 접수를 기록했지만, 약 30초 뒤 A의 중단 요청을 받았습니다. Finish와 B Claim 기록은 없습니다. 따라서 이 기록으로 B 화면이나 GPU 초기화가 원인이라고 판단할 수 없습니다. 당시 클라이언트의 정확한 수신 오류 코드는 남아 있지 않아 근본 원인의 확정에는 새 실행이 필요합니다.

## 수정

- 두 조각 다운로드 응답을 받다가 시간 초과 또는 수신 실패가 발생하면, 같은 오프셋과 발급된 권한으로 한 조각 다운로드에 전환합니다. 전체 요청·흐름 기한은 연장하지 않습니다. 인증 거절, 암호화·형식 오류, 해시 불일치는 이 복구 대상이 아닙니다.
- A의 다운로드·쓰기·파일 고정 단계를 구분하고, B의 파이프 수신·자체 검사·Claim 실패 단계가 일반 종료 코드 1로 덮이지 않도록 합니다. 웹 실행 기록에 숫자 단계의 의미를 표시합니다. 진단은 실행 승인이나 만료 갱신 권한을 갖지 않습니다.
- DLL 모듈 기준 등록은 원본 DLL을 저장하지 않으므로, 디스크 예약을 DLL 크기에서 메타데이터 JSON의 원자적 재작성량으로 변경합니다. 저장 직전에 실제 직렬화 크기를 다시 검사합니다.
- 저장공간 거절 응답과 보안 운영 화면에 가용 공간, 안전 여유분, 작업 예약량과 부족분을 표시합니다. OS 파일시스템 용량과 Railway 볼륨 설정 한도를 구분합니다.

## 저장공간 경고의 의미

`RESOURCE_DISK_RESERVE`는 새 작업 후 남는 공간이 안전 여유분보다 작다는 뜻입니다. 디스크가 완전히 찼다는 뜻은 아닙니다. 기본 안전 여유분 256MiB를 유지합니다. DLL은 RAM에서 측정하며 해시와 기준 정보만 저장합니다. EXE 업로드의 원본 저장량 예약은 유지합니다.

운영 점검 당시 Railway 볼륨 설정은 500MB였습니다. 배포 파일 6개의 합계는 87,782,400바이트였고, 기존 보관·참조 규칙으로 정리 가능한 후보는 0개였습니다. 감사·폐기·라이선스·실행 이력은 삭제하지 않았습니다. 안전 여유분이 계속 부족하면 Railway 볼륨 설정에서 용량 확대가 필요합니다. 이 수정은 볼륨을 유료 증설하거나 안전 기준을 낮추지 않습니다.

## 적용과 검증 범위

서버 변경은 GitHub/Desktop 배포 대상입니다. Windows 실행 파일은 같은 전체 소스에서 A/B/O를 Win64 Release로 Rebuild한 뒤, 최종 파일을 기존 승인·등록·조합 검증 절차로 적용하고 새 A를 발급해야 합니다. 서버 배포만으로 기존 EXE가 교체되지는 않습니다.

서버 회귀·다운로드 경계·소스 계약 검사는 별도 검증 결과와 함께 제공됩니다. 현재 환경에는 Windows와 RAD Studio가 없으므로 dcc64 컴파일, Windows 10/11의 실제 B 실행 및 A/B/O 인계 성공을 검증한 것으로 해석하면 안 됩니다.

최종 취합 검사: 다운로드 복구·모듈 기준 공간·오류 UI·수명주기 단계·네이티브 시작 연결 29개 통과(건너뜀 0). 신규 A/B 단계 계약의 음성 변형 9개도 통과했습니다. 기존 Bootstrap 24개, Overlay 다운로드 7개 및 인접 계약 55개를 확인했습니다. 역할별 API 계약은 A 220 / B 272 / O 268로 유지됩니다. UI 묶음·소스 SHA-512·패키지 파일/모듈 참조 검사는 실제 실행을 대신하지 않습니다.
