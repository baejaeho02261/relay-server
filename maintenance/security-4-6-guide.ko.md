# GameConnect / GameWeb 보안 개선 4–6 적용 안내

작성: 2026-10-17. 기준본: `GameConnect_GameWeb_Security_1-3_Server.zip`.
누적 전체본: `GameConnect_GameWeb_Security_1-6_Server.zip`.
변경 파일 ZIP은 **1–3 수정본에 대한 차이**이며 최초 원본에 바로 덮어쓰는 패치가 아닙니다.

## 먼저 확인할 사항

이번 결과는 코드 변경과 아래 시험까지입니다. 운영 서버, DNS, 방화벽, 사용자 계정, 실제 개인키는 변경하지 않았습니다. 지원 Node 버전과 실제 SQLite 환경의 전체 통합 시험, Delphi 컴파일, 실제 Windows A/B/O 실행은 미완료입니다. A+ 인증이나 임의의 로컬 패치 방지 보증이 아닙니다.

이번에는 Windows 제품 소스 **6개**가 바뀌었습니다. 1–3번과 달리 서버만 교체해서 로컬 측정 개선까지 적용됐다고 볼 수 없습니다. 동일한 전체 소스로 A/B/O를 모두 **Build / 재빌드**하고, 이전 DCU와 혼합하지 마십시오. 측정 상태 열거형의 기본값을 변경했으므로 부분 컴파일/구버전 DCU 혼용을 피해야 합니다. 서명된 통신 필드의 이름·암호 서명 도메인은 유지하며 상태 문자열 `NOT_MEASURED`가 추가됩니다.

기존 IDE 수동 빌드 → 최종 EXE 승인/서명 → 게시 절차를 유지합니다. 필수 CI를 새로 도입하지 않았고, 서명키 생성·재생성·교체도 하지 않았습니다. 프로젝트 설정 파일과 의존성 잠금 파일은 바꾸지 않았습니다. 1–3의 HTTPS 필수 설정은 그대로 유지됩니다.

## 구현 방식과 서버/로컬 경계

새 프레임워크나 npm 의존성을 추가하지 않았습니다. 기존 Node.js 서버 위에서 URL/주소/길이/플래그/허용 상태를 직접 검사하고, 기본 DNS·TLS·HTTPS·crypto 기능을 사용합니다. **C/C++/어셈블리로 서버 전체를 재작성한 결과는 아닙니다.** 기존 `web-push`는 암호문과 VAPID 헤더 생성에만 사용하고 실제 네트워크 연결은 새 제한된 전송 코드가 담당합니다. 자체 암호 알고리즘을 새로 만들지 않았습니다.

권한·정책·승인 판정은 서버가 소유합니다. 새로운 로컬 자격 증명 파일, 성공 결과 캐시, 브라우저 저장소를 추가하지 않았습니다. 로컬에는 자기 실행 파일/코드의 측정, 초기화, 제한된 보고를 위한 코드와 실행 중 메모리가 필요합니다. 기존 패스키 개인키·쿠키·기기 키·기존 데이터 전체를 삭제하거나 서버로 옮기는 작업은 하지 않았습니다. 이미 받은 코드/데이터를 서버가 물리적으로 회수할 수 있다는 뜻도 아닙니다.

## 4. 푸시 목적지 제한

### 변경 파일

- 신규 `GameWeb/services/pushDestination.js`: 주소·DNS·IP 검증.
- 신규 `GameWeb/services/pushTransport.js`: 검증된 목적지로만 직접 TLS 전송.
- 변경 `GameWeb/services/pushManager.js`: 등록/복원/매 전송 재검증 및 새 전송기 사용.

### 기본 허용 범위

환경 변수를 지정하지 않으면 다음 호스트만 허용합니다.

| 서비스 주소 범위 | 정책 |
|---|---|
| `fcm.googleapis.com` | 정확한 호스트명 |
| `updates.push.services.mozilla.com` | 정확한 호스트명 |
| `web.push.apple.com` | 정확한 호스트명 |
| `<한 개 DNS 라벨>.notify.windows.com` | 코드에 고정된 WNS 공급자 범위. `*.windows.com` 전체가 아님 |

이 목록은 코드가 허용하는 범위이며 모든 브라우저/공급자의 실제 전달 성공을 시험했다는 뜻이 아닙니다.

선택적으로 서버 환경 변수 `WEB_PUSH_ALLOWED_HOSTS`에 쉼표로 구분한 정확한 FQDN을 지정할 수 있습니다. 지정하면 기본 목록과 WNS 하위 도메인 규칙을 **대체**합니다. URL, 포트, 임의 와일드카드, IP/CIDR, 내부 주소 허용 옵션은 지원하지 않습니다. 비워 둔 변수를 추가하지 말고, 기본값을 쓸 때는 아예 미설정으로 두십시오.

예시(기본 WNS 범위를 제외하고 아래 세 호스트만 사용할 때):

```ini
WEB_PUSH_ALLOWED_HOSTS=fcm.googleapis.com,updates.push.services.mozilla.com,web.push.apple.com
```

### 전송 처리

HTTPS 443만 허용하고 사용자 정보, 혼동 가능한 authority, 비표준 포트, 루트 경로, 역슬래시·공백·fragment 등은 거절합니다. 저장된 구독도 등록 시 검사만 믿지 않고 매번 검사합니다. 구독 키 길이/형식과 P-256 공개키도 확인합니다.

매 전송에서 A/AAAA를 확인하고, 반환된 주소 중 하나라도 사설·루프백·링크로컬·예약/전환 주소 등 거절 범위에 속하면 보내지 않습니다. IPv6도 별도로 검사합니다. 확인한 **숫자 IP에 직접 연결**하므로 HTTP 라이브러리가 주소를 다시 해석하는 우회 경로를 사용하지 않습니다. 원래 호스트명은 Host/SNI와 인증서 이름 확인에 유지합니다. TLS 인증과 실제 소켓 상대 주소를 확인하기 전에는 HTTP 헤더·본문을 보내지 않습니다.

리디렉션을 따르지 않습니다. 프록시/환경변수 기반 우회, 재사용 연결 풀, 검사하지 않은 다른 주소로의 자동 재접속도 사용하지 않습니다. DNS 장애나 일부 주소 계열의 장애 시 보안 검증을 풀지 않고 실패할 수 있습니다. 프록시 전용 외부망 환경은 직접 연결을 허용하는 배포 구성 없이는 동작하지 않을 수 있습니다.

제한: DNS 최대 3초, 전송 전체 최대 10초, 동시 전송 최대 8개, 평문 payload 최대 3,072바이트, 응답 헤더 최대 8,192바이트, 응답 본문 최대 16,384바이트. 자원 상한 초과는 실패로 처리합니다. 기존 실패 누적/404·410 구독 제거 정책은 유지됩니다. 정책에 맞지 않는 기존 구독은 복원에서 제외될 수 있으므로 관리자 브라우저의 알림 재등록이 필요할 수 있습니다.

이것은 애플리케이션 계층의 방어입니다. 실제 외부 송신 방화벽, 프록시, DNS 서버는 이 작업에서 변경하지 않았습니다.

## 5. 보호 작업의 서버 권한 검사

기존 세션·기기·라이선스·배포 승인·측정 Gate를 없애지 않았습니다. 특히 초기 파일 전달 전에 아직 생성되지 않은 B/O의 측정을 요구하는 순환 의존성을 만들지 않았습니다.

| 경로 | 권한 근거와 이번 처리 |
|---|---|
| 관리자 런처 파일 | 관리자 웹 인증/HTTPS 유지. 서버 런처 상태·기한·배포 정책을 파일 생성/검증 이후 다시 확인 |
| A → B 파일 조각 | 유효한 다운로드 티켓·실제 flow·승인된 A/B/O 구성. 파일 읽기 후, 영속 수신 기록 처리 시, 응답 직전에 재검사 |
| A finish / B claim | 기존 키 소유 증명·다운로드 완전성·A 측정/기기·인계 검증 유지. 런타임 구성 검사에서 각 배포 파일의 취소/정책을 명시적으로 재확인 |
| 라이선스 사용/검증/O 준비 | 기존 실제 라이선스 처리와 `Gate` 유지. matching hash가 있어도 현재 측정 승인이 없으면 거절. 기존 요청 목적 catalog 유지 |
| B → O 파일 조각 | 티켓·부모 세션·라이선스·승인 구성. 읽기 이후와 응답 직전 재확인 |
| O 갱신 | 기존 `Verify`/`RenewalIdentity` 유지. 같은 관측의 재전송은 원래 응답/만료만 반환 |
| B → O 최종 전환 | 최근 `authorizedAt` 값만 보지 않고 O의 현재 `verify` 승인을 전환 전과 상태 변경 안에서 확인 |
| 기기 정책·증명 처리 | 직접 Handle 호출에도 알려진 action과 현재 서비스 가용성을 확인 |
| 보안 challenge/submit | 기존 세션·기기·서명·nonce·정책 경계 유지. 6번의 완전성/새 세대 검사 강화 |
| 일반 SERVER 업데이트 링크 | HMAC·기한뿐 아니라 실제 카탈로그의 enabled 상태 확인. 파일 stat 이후 응답 시작 전 재확인 |
| 종료/중단/진단/거절 영수증 | 기존 자격 증명이 필요하나 최신 측정 실패 때문에 정상 종료나 진단까지 막지 않음. 이 경로로 새 사용 권한/갱신은 발급하지 않음 |

`desktopRequestProtocol.Resolve`의 목적 분리는 유지하고 Bootstrap/Overlay/Device 진입점에서도 알려진 목적을 확인합니다. 클라이언트의 `normal`, `proceed` 같은 임의 필드를 권한으로 채택하지 않습니다.

업데이트 URL은 서버가 서명한 한시적인 다운로드용 bearer capability입니다. 라이선스나 기기 인증 토큰이 아니며, 다른 보호 API 권한을 주지 않습니다. 이번 재검사는 응답 시작 경계까지입니다. 이미 시작된 일반 업데이트 파일 스트림의 모든 패킷을 중간 회수하는 변경은 하지 않았습니다.

### 1–3 기준본에서 함께 수정한 회귀

`desktopConnect.js`에 삭제된 `Rate(...)` 함수를 부르는 구문이 남아 있었습니다. deviceId를 포함한 요청이 디스패치 단계에서 실패할 수 있는 결함이므로 이번에 바로 수정했습니다. 새 `desktopRequestRate.js`는 **기기별 40회/60초, 최대 12,000개**의 분리된 단조시간 예산입니다. 차단된 요청이 창을 연장하지 않고, 한 기기의 초과가 다른 기기의 카운트를 직접 소모하지 않습니다. 앞서 바꾼 TCP 전체/IP 입장 제한은 복구하지 않고 그대로 유지했습니다. 실제 Dispatch 함수에 deviceId가 있는 요청을 넣어 정상 handler 도달과 이후 권한 거절을 시험했습니다.

## 6. 미측정·미완료를 성공과 구분

### Windows 변경(6개 제품 소스)

`Game.Measurement.pas`, `Game.OwnMeasurement.pas`, `Game.ServerAuthority.pas`, `Game.Api.pas`, `Game.Bootstrap.pas`, `Game.Overlay.Client.pas`.

열거형 기본 상태를 `msNotMeasured`로 바꿨습니다. 수집기 진입부와 실제 호출 네 곳 모두 결과/상태를 초기화합니다. 파일·코드 digest의 길이와 크기/구간 수, 정해진 9개 CRC 역할, 전체 완료 metadata를 확인하는 `OwnMeasurementComplete` 검사를 추가했습니다. 일부 성공한 값만 남은 실패 결과는 성공 증거로 사용하지 않습니다.

실패하면 전체 파일/코드 digest를 비우고 미완료 상태를 보고합니다. 정상 진단을 위해 실패한 역할 정보가 남을 수는 있지만 사용 승인을 위한 성공 캐시는 새로 만들지 않았습니다.

### 서버 변경

`measurementStatus.js`, `measurementPlanContract.js`, `desktopSecurityAuthority.js`에서 미측정과 완전성 검사를 일관되게 적용합니다.

- metadata 검사 함수의 false 반환을 무시하던 경로를 실제 거절로 변경했습니다.
- 정상 own metadata 검사에 CRC 층을 전달하지 않던 호출도 수정하여 정상 FULL 결과와 불완전 결과를 구분합니다.
- **인증과 입장 제한을 통과한 새 challenge**가 만들어지면 같은 역할/세션/intent/binding의 기존 판정과 복구 영수증을 지웁니다. 이전 미제출 challenge도 새 세대를 덮어쓰지 못합니다.
- 새 수집이 생략되거나 실패하면 그 작업의 이전 PASS로 권한을 얻을 수 없습니다. 다른 작업 binding의 현재 결과까지 무차별 삭제하지는 않습니다.
- `NOT_MEASURED`, 실패, 누락된 필수 metadata, 불완전 CRC는 승인/갱신 근거가 되지 않습니다.
- 기존 기본 `enforce` 모드는 유지됩니다. `observe`에서도 **측정 없음/불완전은 허용하지 않도록 강화**했습니다. 다만 명시적 observe 정책에서 완전히 수행됐지만 기준과 다른 측정을 관찰용으로 허용하는 기존 의미는 남습니다. 운영 허용 기준으로 삼으려면 enforce를 유지하십시오.
- 기존 서버가 승인한 legacy artifact의 capability가 0인 경우 metadata 생략 호환은 유지합니다. 임의 클라이언트 필드로 새 빌드를 legacy로 전환하지 못합니다. legacy에서도 완전한 측정/CRC와 현재 관측이 필요하며, 제출한 metadata가 잘못되면 거절합니다.

프로그램 사용자에게 관리자/커널 수준 제어권이 있으면 측정기를 바꾸거나 거짓 보고를 서명하게 만들 수 있습니다. 이번 변경은 미초기화·누락·이전 성공 재사용을 방지하는 것이지 사용자 PC의 실행 상태를 신뢰된 하드웨어로 증명하는 것은 아닙니다. 관측 신선도/서명과 측정 내용의 진실성은 구분해야 합니다. 임의의 RET 패치가 전부 탐지된다고 주장하지 않습니다.

4분 50초 다운로드 제한, 기존 하트비트 예약 간격, 기본 B/O 세션 수명은 이번 범위에서 변경하지 않았습니다.

## 적용 순서

1. 기존 운영 데이터/설정/인증서/승인키는 별도 백업하고, 누적 전체 ZIP을 별도 소스 폴더에 풉니다. 운영 DATA_DIR에 전체 소스를 무작정 덮어쓰지 않습니다.
2. 1–3 가이드의 관리자 HTTPS/RP/origin 설정을 유지합니다. 푸시 기본 목록으로 충분하면 새 환경 변수를 추가하지 않습니다. VAPID 키는 기존 키를 그대로 사용합니다.
3. `GameWeb/package.json`에 선언된 지원 Node 버전과 기존 잠금 파일의 의존성을 설치한 검증 환경에서 아래 시험을 실행합니다. 실제 의존성 확인 실패를 0건/성공으로 해석하지 않습니다.
4. 같은 최종 소스로 Windows A/B/O를 모두 재빌드하고 기존 승인·서명·게시 절차로 검증합니다. 반영 후 새 런처/새 세션으로 정상 시작·라이선스·갱신·O 전환을 확인합니다. 자동 CI를 새로 강제하지 않습니다.
5. 정상 동작 이후 미측정/보고 중단/다운로드 지연/권한 취소 상황을 별도 시험 환경에서 재현하고 서버가 새 권한을 거절하는지 확인합니다. 운영 환경에 부하나 실제 알림을 대량 전송하는 시험은 이 패치에 포함하지 않습니다.

```text
# 추출 루트에서(소스 일치 검사)
python GameWeb/scripts/verify-source.py

# GameWeb 폴더에서
npm run test:security:123
npm run test:security:456

# OpenSSL 실행 파일이 있는 검증 환경: 실제 루프백 TLS 검사
npm run test:security:456:tls

# 실제 SQLite/지원 런타임 필요: 이 작업 환경에서는 완료하지 못한 통합 검사
node scripts/test-desktop-deadlines.js
node scripts/test-security-authority.js
```

Windows 전용 수집기 probe: `GameConnect_Win64/tests/MeasurementCompletionProbe.dpr`. IDE 검색 경로에 부모 `GameConnect_Win64` 소스 폴더를 포함하여 별도 테스트 프로젝트로 빌드/실행합니다. 배포용 제품 파일이 아니며 이 환경에서는 실행하지 않았습니다. 기본 미측정 상태, 없는 수집 계획의 실패, 남아 있던 digest 제거, 실패 bundle의 거절을 확인하도록 작성했습니다.
